# screenlock-pin

A PIN for the KDE Plasma lock screen, within limits. Two words run through everything here:

- **password:** your account password. It is long, it works everywhere, always, and stock `pam_unix` checks it.
- **PIN:** a short extra secret, of any characters. It unlocks the lock screen and nothing else, from boot on, while it is **enabled**. Three consecutive failures **pause** it: the password is required, and the next password unlock at the lock screen unpauses it. Failures nobody forgave, counted across days and reboots, **disable** it until root turns it back on or sets a new PIN, as the failure budget section below explains.

Login, sudo, polkit, TTY and SSH never see the PIN. The full rules, the threat model and the reasoning live with the Python proof of concept in `poc-py/` (its README, WALKTHROUGH.md and docs/), which this Rust version followed rule for rule until it dropped the pepper, the expiry and the password after every boot (`docs/chaos/security-target.md` at the repo root says why), and with one change of architecture: the PIN hashes and the failure counts are reachable only by a `screenlock-pin` system group with no members, and only a PIN checker that is setgid to that group reads them, so nothing the user runs can read a hash or reset a count. The PIN checker section below explains it, and `docs/chaos/threat-insider-hash-leak.md` at the repo root explains why.

**Status: installed on one test VM, not on a machine anyone relies on.** Everything builds and runs in `target/`, temporary directories and a podman container. The installer, `packaging/install.sh`, is tested against a fake root and, as root, inside a stock Fedora 44 container; no recipe runs it anywhere else. On 2026-10-15 it was run by hand in an Aurora VM, and the PIN worked at the real Plasma 6.7.5 lock screen under SELinux enforcing; `docs/chaos/aurora-vm-test.md` at the repo root has what was tested and what wasn't.

## Try it

```
just demo     # set, the PIN at once, three failures pause it, the password unpauses it (through the real PIN checker)
just test     # every test: rules, files and hashing, the CLI, the PAM stack
just smoke    # only the PAM stack, through the system's libpam
just lint     # clippy with warnings as errors, and a formatting check

```

## Crates

| Crate | Folder | What it is |
|---|---|---|
| `screenlock-pin-core` | `crates/core` | The rules, with no I/O and no `unsafe`: settings and their ranges, the failure budget (`Budget`), which also holds the consecutive count, the two reasons the PIN is refused (`Refusal`: paused or disabled), and one unlock attempt (`try_unlock_with_pin`, returning a `Verdict`) or the PIN unpause after a password unlock (`unpause_pin_after_password_unlock`). Files, clock and hashing come in through the `Store`, `Clock` and `Hasher` traits. |
| `screenlock-pin-sys` | `crates/sys` | Those traits on a real machine: `UserFiles` (trusted-file checks on the open file, atomic writes, a lock with a timeout, the budget in a sticky directory of the PIN checker's group, where each user's files must be that user's own), `Yescrypt` (the system's libxcrypt, which also compares a new PIN with the password's hash in `/etc/shadow`), `SystemClock` (the wall clock), and account, group and shadow lookups. |
| `screenlock-pin-checker` | `crates/checker` | The setgid program that holds the hashes and counts: `check`, `unpause` (after a password unlock, with no password) and `status`. `lib.rs` decides, with every location passed in, so the tests drive it directly; `main.rs` is the setgid entry point; `secure.rs` holds all of its `unsafe` code (the clean start, `AT_SECURE`, syslog). |
| `pam_screenlock_pin` | `crates/pam` | The PAM module the lock screen would load: on the `check` line it reads what was typed, pipes it to the PIN checker the way pam_unix feeds `unix_chkpwd`, and maps the exit code; on the `after-password-auth` line it asks the PIN checker to unpause the PIN from `pam_sm_setcred`, with nothing on the pipe. `pam.rs` holds all of its `unsafe` code: the two entry points, `pam_get_user`, `pam_get_authtok`, `pam_syslog` and the SIGCHLD guard. | `screenlock-pin-cli` | `crates/cli` | The `screenlock-pin` command: `set`, `enable`, `remove`, `restore-defaults` and `doctor` (as root), and `status`, which asks the PIN checker. `doctor.rs` judges every user's files by the PIN checker's own rules. |
| `pamharness` | `crates/pamharness` | Test-only: a PAM client that runs `pam_authenticate` through the real libpam the way kscreenlocker does (one session for many attempts, `pam_setcred` after a success, a fail-delay callback that records instead of sleeping), with service files from a temporary directory (`pam_start_confdir`) or the system's own (`pam_start`, as the lock screen does), and the SIGCHLD settings real hosts have (`host`). |
| `brokenpin` | `crates/brokenpin` | Test-only: deliberately broken stand-ins for the module (panics, segfaults, sleeps, says yes, lacks its entry point) and the PIN checker (says yes, sleeps), which the uninstall cases install under the real names. |
| `screenlock-pin-systest` | `crates/systest` | Test-only: `install.sh` against a fake root (`tests/install.rs`), and the scenarios the container runs (`src/main.rs`). |

## The PAM files

The lock screen's PAM file, `/etc/pam.d/kde`, changes in one word: its stock line `auth substack password-auth` becomes `auth substack screenlock-auth`. `screenlock-auth` is screenlock-pin's own PAM file, `packaging/screenlock-auth.pam`, which `install.sh` puts into `/etc/pam.d` and which does nothing until `kde` names it. It holds the stock line, between screenlock-pin's two:

```
# /etc/pam.d/screenlock-auth
auth        sufficient    /usr/local/lib64/security/pam_screenlock_pin.so check
auth        substack      password-auth
auth        optional      /usr/local/lib64/security/pam_screenlock_pin.so after-password-auth
```

```
# the auth lines of /etc/pam.d/kde on Fedora, once integrate-into-pam.sh add has changed the first
auth        substack      screenlock-auth
auth        include       postlogin
```

`kde` pulls the file in with `substack`, so a correct PIN ends `screenlock-auth` alone, and `kde` goes on to its `postlogin`, as after the password. The stock `password-auth` stays exactly as authselect writes it. Since only one word changes, `integrate-into-pam.sh remove` gives back the stock `kde` byte for byte. The one new risk is a missing file: while `kde` names `screenlock-auth`, libpam fails every attempt at the lock screen without it, the password too, so `add` refuses until `install` has put the file in place, and `uninstall` refuses until `remove` has changed `kde` back; `sudo` and a text console still work. The stack tests build their PAM stack from this very file, so the control columns tested are the ones that ship, and the container test deletes the file on purpose to show the lock-out and its repair. `docs/where-the-pin-belongs-in-pam-IMPORTANT.md` at the repo root has the reasoning. Not yet built: the module doesn't refuse PAM services other than `kde`, so a program that opens `screenlock-auth` as its own service gets the PIN check, just as one that opens `kde` does today; `docs/chaos/plan.md` has it as a planned item.

`check` asks the PIN checker whether what was typed is the PIN: if so, `sufficient` ends `screenlock-auth` with success; anything else is ignored at once, and the stock stack checks the same input as the password, exactly as it would without screenlock-pin, faillock included where it is on. The module asks for the input itself, and the stock `pam_unix` takes the answer it got, so the lock screen asks once. `after-password-auth` works in `pam_sm_setcred`, not in `pam_sm_authenticate`, which on that line does nothing and never reads what was typed. libpam calls `pam_sm_setcred` only when the lock screen calls `pam_setcred`, which kscreenlocker does after a successful unlock only, and only on the lines `pam_authenticate` went through: after a PIN unlock the `check` line ended it, and after a failure there is no `pam_setcred` at all. So the `after-password-auth` line hears exactly the password unlocks, and the stock stack alone decides whether the password was right, faillock and sssd included. The PIN checker then forgives the failures of the last 90 seconds, among them the password itself when it was short enough to be checked as a PIN, and starts the consecutive count over, which unpauses the PIN. For the replay to stop at the `check` line after a PIN unlock, that line's `pam_sm_setcred` answers `PAM_SUCCESS`: libpam goes on past a `sufficient` line that answers `PAM_IGNORE` there. `docs/current-setcred.md` at the repo root has the reasoning, and how it was tested on a real lock screen.

The lines name no other path: the module runs the PIN checker from where `install.sh` puts it, `/usr/local/libexec/screenlock-pin/screenlock-pin-checker`, and the PIN checker reads `/etc/screenlock-pin`. The tests point both elsewhere, the module with `pin_checker=` in the PAM line, which only root can write, and the PIN checker with its `--dev-*` options, which it refuses under setgid. The module's path is spelled out because libpam only finds a bare module name in its own directory, under the read-only `/usr` on Fedora Atomic. A PAM line the module can't read, such as another version's after an upgrade, refuses the PIN alone: the module still asks for the input before stepping aside, so the password still works through whatever follows.

A correct PIN never unlocks sooner than 75 ms after the PIN checker started: the PIN checker waits out the rest before it answers, once the budget is saved and its lock released. kscreenlocker 6.8 times every `pam_authenticate` and takes an answer within 50 ms for a broken authenticator, and a correct PIN takes only about 20 to 25 ms. Nothing else waits: a wrong PIN, a password or a refusal goes on to the stock stack at once, and `pam_unix` is slow anyway. Waiting leaks nothing, since the unlock shows. The time is `min_milliseconds_before_pin_unlock` in `/etc/screenlock-pin/config` (0 to 1000; under 50 breaks the PIN on 6.8). The wait comes from a timer, not from the hash cost, so a faster CPU can't bring a correct PIN back under 50 ms.

## Files, once installed

| Path | Holds | Owner and mode |
|---|---|---|
| `/etc/screenlock-pin/config` | Every setting, one policy for all users; optional | `root:root 0644` |
| `/etc/screenlock-pin/users/` | One file per user with a PIN | `root:screenlock-pin 0750` |
| `/etc/screenlock-pin/users/<user>` | That user's yescrypt hash, and nothing else | `root:screenlock-pin 0640`: the PIN checker reads it, nobody else but root |
| `/var/lib/screenlock-pin/` | Every user's failure budget, on disk, so it survives reboots; kept in shape by `/etc/tmpfiles.d/screenlock-pin.conf` | `root:screenlock-pin 1770`: only the group can enter, and the sticky bit lets each file be replaced or deleted only by its owner |
| `/var/lib/screenlock-pin/<uid>.budget` | The consecutive count, failures waiting to be forgiven, suspicious failures of the last 7 days, the total since the PIN was set, whether it is disabled, and when the PIN was set and last became enabled or paused | `<uid>:screenlock-pin 0600`: the user it describes owns it, but can't enter the directory to reach it |
| `/var/lib/screenlock-pin/<uid>.lock` | Keeps two attempts from interleaving | `<uid>:screenlock-pin 0600` |
| `/usr/local/libexec/screenlock-pin/screenlock-pin-checker` | The PIN checker | `root:screenlock-pin 2755` (setgid only) |
| `/etc/sysusers.d/screenlock-pin.conf` | The `screenlock-pin` system group (`g screenlock-pin -`): no members, no account | `root:root 0644` |
| `/etc/pam.d/screenlock-auth` | screenlock-pin's PAM file: the PIN check, then the stock `password-auth`; used only once `/etc/pam.d/kde` names it | `root:root 0644` |

The format is poc-py's `key = value` lines, and the hash is the same `$y$` yescrypt string, so a poc-py user file's `hash = ...` line carries over as is. Settings were renamed to the new vocabulary: `max_failed_unlocks` is now `max_failures`, `min_length` is `min_pin_length`, `min_letters` became `required_non_digits_count`, and `hash_cost` is unchanged; `max_short_password_len` (later `max_pin_length`) and `expiry_hours` are gone, and so are per-user settings. An unknown setting is an error, and so is any setting in a user's file, so an old name or an old file can't be silently ignored.

## Installing

From a clone, as yourself (not with sudo; the recipes ask for sudo themselves):

```
just install               # build in podman, then install.sh install and check; run it again to update to what is checked out
just integrate-into-pam    # one word of /etc/pam.d/kde, after a diff and a yes: password-auth becomes screenlock-auth; the PIN works from then on
just logs                  # print screenlock-pin's journal lines of the last 30 minutes and how it is set up, to paste into a report; just logs "2 hours ago"
just check                 # install.sh check
just remove-from-pam       # that word changed back, after a diff and a yes
just uninstall             # install.sh uninstall, once remove-from-pam has run
```

`install` never changes `/etc/pam.d/kde`: editing the lock screen's PAM file on a machine it doesn't know is too much to do unasked, so that is `integrate-into-pam`'s alone, and only when run. `install` only adds screenlock-pin's own `/etc/pam.d/screenlock-auth`, which nothing uses until then. Underneath, `packaging/install.sh` has four commands, and `packaging/integrate-into-pam.sh` three:

```
just release                                  # the build, with Fedora 44's toolchain in a podman container, into target/screenlock-pin
packaging/install.sh check-build              # what the built files load; release runs it, and install runs it again
sudo packaging/install.sh install             # the files, /etc/pam.d/screenlock-auth among them, checked; then whether /etc/pam.d/kde has screenlock-pin's line
sudo packaging/install.sh check               # kind, mode, owner, bytes, SELinux label and what the binaries load; the group empty and locked; /etc/pam.d/kde stock or with screenlock-pin's line
sudo packaging/install.sh uninstall           # the files, once /etc/pam.d/kde has nothing of screenlock-pin's
sudo packaging/integrate-into-pam.sh add      # after a diff and a yes: auth substack password-auth in /etc/pam.d/kde becomes auth substack screenlock-auth
sudo packaging/integrate-into-pam.sh remove   # after a diff and a yes: that line back as it was
packaging/integrate-into-pam.sh check         # whether /etc/pam.d/kde has screenlock-pin's line, nothing of screenlock-pin's, or anything else
sudo screenlock-pin set                            # choose the PIN, typed twice; the lock screen takes it at once
sudo screenlock-pin enable                         # only if too many suspicious failures disabled it
```

When a PIN doesn't work, `screenlock-pin status` says why, and so does `sudo screenlock-pin doctor`, for every user at once, with the command that fixes each problem. Doctor changes nothing, and there are no repairs, only these commands:

```
sudo screenlock-pin doctor                    # what makes the lock screen refuse a PIN, whose, and which command fixes it
sudo screenlock-pin remove [--user NAME]      # that user's PIN, budget and lock file, whatever state they are in, even for an account that is gone
sudo screenlock-pin remove --all              # every PIN and budget, after a question: the blank page
sudo screenlock-pin restore-defaults          # the global config deleted, after showing it and a question: every setting back to its default
```

Each user's file, budget and lock file concern that user's PIN alone, and a problem with one refuses that PIN alone. Doctor runs as root, which reads everything, so its rules include the ones the PIN checker never meets because it couldn't open the file at all: a user file its group can't read, a lock file its owner can't open. A file in `users/` whose account is gone is nobody's PIN, but doctor names it anyway, since an account made later with that name would get it.

The build matters as much as the install: the module runs inside the lock screen and the PIN checker with the `screenlock-pin` group, so each must load its libraries from the system's own directories, which only root can change. A toolchain such as Homebrew's can write into a binary a library search path of its own (an RPATH or RUNPATH), or link it against its own libraries under `/home/linuxbrew`, which belongs to a user, who could then put code into both. So `install` first checks each of the three files with `readelf` and `ldd`: no search path of its own, the system's loader, and every library found under `/lib`, `/lib64`, `/usr/lib` or `/usr/lib64`. A build that fails is refused before anything changes, and `check` applies the same rule to the installed copies. The check judges the files, not how they were made, so any toolchain that builds them clean will do; `just release` is the way that always does, because it builds in a Fedora 44 container whatever the machine has. `readelf` comes with binutils, which every Fedora with gcc has, Aurora included; without it `install` refuses. `--from DIR` installs a build from elsewhere, such as a plain `cargo build --release` in `target/release`, under the same check.

`install` is also how to upgrade, and running it again is harmless. It replaces each file by a rename, so a lock screen already using screenlock-pin never sees a missing or half-written one, and then removes whatever else is in `/usr/local/libexec/screenlock-pin`, so nothing an older version left there stays; `check` names anything there it didn't ship. It replaces `/etc/pam.d/screenlock-auth` too, which is screenlock-pin's alone, so an edit there doesn't last. It ends by saying whether `/etc/pam.d/kde` has screenlock-pin's line, nothing of screenlock-pin's, or anything else, and leaves that file as it is either way. Pieces that don't fit together, after a failure partway, only ever refuse the PIN: the module steps aside from a PAM line it can't read, after asking for the input, so the password still works. `install` assumes a machine where screenlock-pin is new or already in this layout: it refuses, before it changes anything, where it finds properpin (its files in `/etc/properpin`, `/var/lib/properpin` or `/usr/local`) or lines in `/etc/pam.d/kde` naming properpin or `pam_screenlock_pin.so`, as earlier versions put theirs. Neither `install` nor `check` judges the PINs, the budgets or the config, which `install` doesn't write: a problem there refuses only the PINs it concerns, and `install` ends by printing what `screenlock-pin doctor` finds. With the lines in, a user who hasn't set a PIN sees no difference: the module steps aside. To turn screenlock-pin off for yourself, `sudo screenlock-pin remove`; for the whole machine, `remove-from-pam`, then `uninstall`.

`integrate-into-pam.sh add` changes one word of `/etc/pam.d/kde`: `password-auth` becomes `screenlock-auth` on the stock `auth substack password-auth` line, and whatever spacing or comment that line has stays. It refuses while screenlock-pin isn't installed, since `kde` naming a missing `screenlock-auth` is the one thing that must never be in place, and refuses a file without exactly one stock line, saying which word to change for whoever does it by hand. It changes only a stock file: one with lines of properpin's, of an earlier screenlock-pin's (which named `pam_screenlock_pin.so` in `kde` itself), or with `screenlock-auth` anywhere but on that one line, is refused and left as it is, for you to put back as stock by hand. `remove` changes the word back, so the file is stock again byte for byte, and refuses the same files `add` refuses; nothing ever deletes `/etc/pam.d/kde`. `uninstall` refuses while the file has anything of screenlock-pin's. Then it removes what `install` put in place, `/etc/pam.d/screenlock-auth` among it, including the directories `install` had to create (noted in `/etc/screenlock-pin/install.created-dirs`), and keeps `/etc/screenlock-pin`, with the PINs in it, `/var/lib/screenlock-pin`, with the budgets, and the `screenlock-pin` group those files belong to. `install` creates the group with `systemd-sysusers` where it exists and `groupadd --system` otherwise; no user is ever created. `check` on the real system needs root, because it also reads `/etc/gshadow`: it fails when the group has members, is anyone's primary group, or has a password that isn't locked, since any of those would give someone the group without running the PIN checker. The installed `screenlock-pin` command is a two-line wrapper that passes this machine's paths to the real binary in `/usr/local/libexec/screenlock-pin/`.

Upgrading from properpin, as screenlock-pin was called until 2026-10-18, is by hand: nothing reads its paths, its group or its PAM lines, and `install` refuses while they are there. Take its lines out of `/etc/pam.d/kde`, uninstall it with its own `install.sh`, from a checkout before the rename, then install screenlock-pin and set the PIN again. The same goes for an earlier screenlock-pin whose lines named `pam_screenlock_pin.so` in `/etc/pam.d/kde`: take those lines out by hand, and install again. Its config, if it was changed, can be copied from `/etc/properpin/config`; a config or PIN from a version with a pepper is named by `screenlock-pin doctor`, which `install` runs at the end, with the fix for each.

## The PIN checker

`screenlock-pin-checker` is to screenlock-pin what `unix_chkpwd` is to pam_unix: a small program with more rights than its caller, which reads the secret on a pipe and answers with an exit code. It is owned by root and setgid to the `screenlock-pin` group, as Debian's `unix_chkpwd` is setgid to `shadow`: it runs as its caller, with the group added, so the caller can't change the binary, and nothing can log in as screenlock-pin, because no such account exists. The group has no members and a locked password, so running the PIN checker is the only way to get it. The PIN checker never takes a user name or a path from its caller: the caller is the real uid the kernel reports. Each user's counts file belongs to that user, in a sticky directory, so one user's run of the PIN checker, even an exploited one, can't read, replace or delete another's, and a counts or lock file planted in someone else's name is refused. Before anything else it puts the process into a known state: stdin, stdout and stderr open, every other file closed, signals reset, the environment cleared, umask 077, working directory `/`, and panics abort without printing.

Anything the user runs can ask the PIN checker to unpause the PIN, which takes no password, and so also forgive its own recent failures. `docs/chaos/security-target.md` accepts that: code running as the user can unlock the session and keylog the PIN anyway, so all it gains is guessing the PIN through the PIN checker a little faster than keylogging it, and the budget's limits on suspicious failures still count every guess nobody forgave in time.

For local tests, the PIN checker accepts `--dev-etc`, `--dev-budget`, `--dev-owner` and `--dev-log`, but only when two independent checks agree that it runs without elevated rights: the kernel's `AT_SECURE` flag is clear, and the real and effective user and group ids are equal (`dev_options_allowed`). Then it has no more rights than its caller, so the caller choosing its files gives nothing away. Installed setgid, any `--dev` option is refused outright, which the container test checks. The stack and CLI tests use this to run the real binary against a sandbox. `docs/chaos/at-secure.md` at the repo root explains the two checks, `docs/chaos/pin-checker-review.md` lists every hazard of a program with more rights than its caller and the code that handles it, and `docs/chaos/concerns.md` holds what is still open.

## Setting a PIN

`sudo screenlock-pin set` asks for the PIN twice, after one line saying it may be up to 64 characters and should differ from all the user's account passwords, and never for the password itself: it runs as root, so it compares the PIN with the user's own hash in `/etc/shadow`, whatever scheme that hash uses, and refuses a match. A user with no entry there (LDAP, systemd-homed) gets a warning instead. Setting the PIN that is already set starts its budget over, total included, so `set` says so and asks first; `sudo screenlock-pin enable` of a disabled PIN asks too, since the failures that disabled it may have been someone guessing it. Without a terminal both refuse, unless given `--yes`.

A PIN has 4 to 64 characters (`min_pin_length`; the 64 is fixed), of which at least 3 aren't the digits 0 to 9 (`required_non_digits_count`, 0 to turn it off): letters of any script, punctuation and spaces all count. Only control characters are refused. These rules apply only at `set`; at the lock screen, everything typed is checked as the PIN, the password included, whatever its length, since a PIN may be as long as a passphrase.

The PIN is hashed with yescrypt at `hash_cost`, and that is all: no pepper, no expiry and nothing in memory, so the PIN works right after a reboot, and a password change leaves it alone. `docs/chaos/security-target.md` at the repo root explains why the pepper went: it only protected the hash from someone holding a copy of the disk but not the running machine, who gains next to nothing from a PIN.

## The failure budget

The consecutive count stops a burst of guesses, but a correct PIN starts it over, so someone with repeated access could guess twice whenever you step away, forever. The budget closes that, without any notification:

- **Every input typed at the lock screen that doesn't unlock is a failure,** wrong passwords included, since the `check` line sees everything before `pam_unix` does. An empty input isn't, and nothing is counted for a user without a PIN.
- **The user's own typos are forgiven:** a correct PIN forgives the failures of the 45 seconds before it (`forgive_before_correct_pin`), the correct password those of the 90 seconds before it (`forgive_before_correct_password`, through `unpause`, after the stock stack accepted it). A correct password typed at the lock screen is itself a failure for a moment, until `unpause` forgives it.
- **A paused or disabled PIN records nothing:** the input isn't checked, so it isn't a guess, and typing at a paused PIN can't push it on to disabled.
- **A failure nothing forgave in time is suspicious.** It is judged at the PIN checker's next run; no daemon is needed.
- **The PIN is disabled** at 10 suspicious failures within 24 hours (`max_suspicious_24h`), 25 within 7 days (`max_suspicious_7d`), or 60 since the PIN was set (`max_suspicious_total`). Disabled, the PIN is refused and the password doesn't bring it back, until `sudo screenlock-pin enable` (same PIN, after asking; recent failures forgotten, the total kept, so it refuses once the total is reached) or `sudo screenlock-pin set` (a fresh budget).
- **It survives reboots:** the budget, consecutive count included, is in `/var/lib/screenlock-pin`, stamped with the wall clock. Whoever can set the clock could age failures out of the 24-hour and 7-day windows, but never out of the total; setting it takes root, which wins anyway, and `docs/chaos/current-concerns.md` at the repo root says why the network and a reboot don't change that.
- **A damaged or foreign budget refuses the PIN** instead of being read as a fresh one; `set` starts it over.

Like every setting, the five live in `/etc/screenlock-pin/config`. `screenlock-pin status` shows the counts, and the journal has a line for each failure that becomes suspicious and for the moment the PIN is disabled. The total limit is what bounds an attacker: whatever their pace, about 60 guesses per PIN, against 60 million two-word PINs or 10,000 four-digit ones.

## Like the lock screen

The module starts the PIN checker from inside the lock screen and needs its exit code, so process-wide state is part of its correctness: the SIGCHLD setting, who reaps which child, and what other threads do meanwhile. The tests run attempts the way kscreenlocker does: one PAM session kept for many attempts, as both 6.7.5 and 6.8 do, with `pam_setcred` after a success. `crates/pam/tests/stack.rs` then has hosts misbehave, each test in a process of its own, since SIGCHLD is one setting for the whole process: a host that ignores SIGCHLD and one whose handler reaps every child both still get every answer and keep their setting; a host thread looping on `waitpid(-1)` takes the PIN checker's exit status, and the PIN fails closed while the password still works; the host's own child, exiting while the PIN checker runs, can still be collected; attempts on four threads at once keep the host's handler; and a panic while SIGCHLD is changed puts it back. The four-thread test found a real race: two threads each saving and restoring SIGCHLD lost the host's handler, so screenlock-pin's attempts now take turns at that point (a mutex in `DefaultSigchld`). Nothing in the real lock screen runs screenlock-pin on two threads at once, and on Fedora no module in the fingerprint or smartcard stacks starts a child, so this was latent. `docs/chaos/harness-closer-to-kscreenlocker.md` at the repo root has the reasoning.

## The container test

`just podman` builds everything with Fedora's own Rust inside a stock Fedora 44 image, takes `/etc/pam.d/kde` from Fedora's plasma-workspace package, installs screenlock-pin with `install.sh` as root (creating the `screenlock-pin` group and the setgid PIN checker) and puts its lines in with `integrate-into-pam.sh`, and then runs `crates/systest` (about a minute). Each PAM attempt runs as the test user, the way the lock screen runs as the locked user, so the module starts the real setgid PIN checker and `pam_unix` checks the password through its own setuid helper `unix_chkpwd`, both for real. The test listens on `/dev/log` itself, so it sees what the module, the PIN checker and `pam_unix` log through syslog. Nothing about this machine changes beyond podman's image storage.

The scenarios: the rollout (the PIN at once, the password's PIN unpause, three failures pausing the PIN in the budget on disk, and a wrong password, which gets no `pam_setcred`, never unpausing it), `set` refusing the password as a PIN through the real `/etc/shadow` and asking before setting the same PIN again, a password change leaving the PIN working, the PIN being refused by every other service (`sudo`, `su`, `login`, `system-auth`, `password-auth`, `passwd`, `other`), files tampered with as root (readable, owned by the user, symlinked, corrupt, a hash in the global config, a shared budget directory, a user file its group can't read, a lock file its owner can't open), each also found by `screenlock-pin doctor` as root, which must find nothing wrong right after set-up, three wrong PINs at once, installing again keeping the PIN and the PAM file and printing doctor's verdict, and `uninstall` refusing while screenlock-pin's lines are in, then `remove` and `uninstall` restoring `/etc/pam.d/kde` byte for byte. Then the PIN checker, attacked as the users would: the user can't read their hash, list the files, or read, delete or replace their counts; another user gets nothing and spends none of the tries; `--dev` options pointing at the user's own files are refused under setgid; a poisoned start (closed stdout and stderr, an extra open file, `LD_PRELOAD` and a hostile environment) changes no answer; `unpause` asked for directly unpauses the PIN, as accepted; `pam_setcred` reaches the `after-password-auth` line after a password unlock only, never after a PIN unlock or a wrong input; a missing PIN checker refuses the PIN while the password still works; `status` shows only the caller's own PIN and refuses root. And the PIN checker's group, played by bob with the group added, as if he had exploited the PIN checker: it can't append to, chmod, rename, delete or replace the PIN checker; it can't read, overwrite, delete, rename or replace alice's counts; a lock file and a budget planted in alice's name before her first attempt are refused, with a log line naming the lock file's owner; and `install.sh check` fails when bob is added to the group or the group's password is emptied, and no `screenlock-pin` user exists. And the budget: a wrong PIN or password followed by the right one leaves nothing behind; the slow attack (a guess, the user's correct PIN two minutes later, again) disables the PIN on the third round with the daily limit at 3; a disabled PIN stays disabled even for the password, until `screenlock-pin enable`, which asks first; the total limit can't be lifted by `enable`, only by `set`; and a damaged budget, or one planted by another user, refuses the PIN. Scenarios backdate the budget's timestamps as root instead of waiting. And the lifecycle of kscreenlocker 6.8: a long-lived worker process serves the password, the PIN, a wrong PIN and the PIN again on one session, only the failure asks for a delay, and the worker exits cleanly after `pam_end`; a worker killed at chosen and random moments while checking a wrong PIN, with SIGKILL or with SIGTERM and SIGKILL 25 ms later as the greeter cancels, never unlocks, its PIN checker finishes on its own, a fresh attempt right after gets the lock, and the logged failures and the budget agree; and a correct PIN never answers sooner than `min_milliseconds_before_pin_unlock`, the default 75 ms and a configured second, while a worker killed during that wait unlocks nothing (the PIN checker has already taken the PIN, so its consecutive count is reset). Every attempt process must exit cleanly, never by a signal, and after every scenario no PIN checker may still be running. The run prints how long a correct PIN takes through the real stack: about 20 to 25 ms of work, padded to the minimum.

Every check that something is absent (no PIN checker left running, nothing of screenlock-pin's in another service's log or after uninstall, no PIN unpause after a PIN unlock or a wrong password) has a positive control: its matcher is derived from the installed file names and shown to find its target in the same run, so a matcher gone stale fails instead of finding nothing and passing. Breaking each matcher on purpose, on 2026-10-17, failed the scenario it guards.

What it can't show: the greeter's own behaviour, SELinux (a container doesn't enforce the host's policy for its files), logind and the journal. The test was checked by breaking things on purpose, before the pepper and the per-boot state were dropped, so some of what follows names what no longer exists: with the middle PAM line set to `default=ignore`, three scenarios fail and the log shows `unix_chkpwd` rejecting the password and the module starting to accept the PIN anyway; with the readable-by-others check removed, its scenario fails; with the PIN checker's `AT_SECURE` check disabled, the `--dev` scenario fails; with `start-accepting-pin`'s password check removed, the scenario on starting to accept the PIN fails, as do two local tests. For the setgid layout: with the sticky bit dropped from the run directory (in `install.sh`, the test's reset and the directory check), bob deletes alice's counts and that scenario fails; with the lock file's owner check removed, the planted-files scenario fails on its log line, though the PIN is still refused, because a state file that isn't the user's own reads as no state; with the `AT_SECURE` half of `dev_options_allowed` removed, its unit test fails while the container's `--dev` scenario still passes on the id comparison alone, which shows the two checks are independent. For the budget: with forgiveness turned into a no-op, the typos scenario and the slow-attack scenario fail, as do four unit tests; with the budget kept in `/run`, the reboot scenario fails because the password starts accepting the PIN again; with a correct PIN clearing the recent failures, the slow-attack scenario and the matching unit test fail. For the lifecycle: with the SIGCHLD guard skipping its restore during a panic, the panic test fails; without the mutex, the four-thread test fails; with `-z nodelete` removed, every container scenario still passes, because glibc keeps a library mapped while it has thread-local destructors pending, so the crash needs a thread that exits after `pam_end`, which the load/unload test in `stack.rs` covers. For the upgrade, on 2026-10-18: with the module made to step aside from a PAM line it can't read without first asking for the input, the scenario with an older version's lines fails on the right password refused, `pam_unix use_first_pass` logging that it "could not identify password".

## The uninstall cases

`just podman-uninstall` tests the way out, not screenlock-pin: in a fresh container per case, it records the stock system (what the lock screen, `sudo`, `su` and `login` answer, `/etc/pam.d` byte for byte, every path under screenlock-pin's directories, the groups), installs a deliberately broken screenlock-pin through `install.sh` under the real names and puts its lines in with `integrate-into-pam.sh add`, checks that it really breaks the lock screen while `sudo` still works, checks that `install.sh uninstall` refuses while the lines are in, runs `integrate-into-pam.sh remove --yes` and `install.sh uninstall`, and checks that the record matches again apart from the documented leftovers. Doing both again must change nothing, and the real screenlock-pin must then install, work and come out just as cleanly. The 9 cases: modules that panic, segfault, hang, unlock everything, lack their entry point, are garbage or were deleted; and PIN checkers that say yes to everything or hang. They found that uninstall left behind the directories `install` had created. Since screenlock-pin's own `pam_unix use_first_pass` line went on 2026-10-18, a module that lacks its entry point, is garbage or was deleted only stops the PIN: libpam skips a module it can't call, and the stock `pam_unix` asks for the password itself. That line, which only read what the module had asked for, was what locked the lock screen. Four cases about a damaged block between markers went with the markers. `docs/chaos/install-uninstall-with-a-broken-screenlock-pin.md` at the repo root has the details, and `docs/chaos/uninstall-test-remaining-ideas.md` what is left.

## Secrets in memory

What was typed is held in `Secret` (`screenlock-pin-core`), which is wiped when dropped and can be neither printed nor cloned. The module copies it out of libpam once, writes it into the pipe to the PIN checker and drops it as soon as the PIN checker has answered; the PIN checker reads it into a buffer of fixed size, which never grows, and wipes it on exit; nothing of screenlock-pin's ever reads the password knowing it is the password; libxcrypt's NUL-terminated input copy and its 32 KB work area are wiped after every hash, and a check compares the computed hash where libxcrypt wrote it, without copying it out. The CLI wraps both entries of `screenlock-pin set` and reads stdin into a buffer that can't grow, and compares the PIN with the password's hash in libxcrypt's work area, which is wiped like any other. This is best effort: libpam's own copy (`PAM_AUTHTOK`, which `pam_unix` reads next and libpam wipes itself; after a correct PIN the module clears it at once, so no later line takes the PIN for the password), the lock screen's copies and the terminal's are out of reach. `docs/chaos/pin-pam-copy.md` at the repo root holds the open question about libpam's copy.

## CI

GitHub Actions runs `.github/workflows/ci.yml` on every push to any branch and on pull requests. It has four jobs, and any of them failing fails the run:

- **Tests (Fedora 44):** `cargo test --workspace --locked` in a `fedora:44` container with Fedora's own Rust, as an unprivileged user, because the module refuses to run as root.
- **System test (podman):** the two commands behind `just podman`, on an Ubuntu runner, with rootful podman (`sudo`): in the runner's rootless podman, setuid `unix_chkpwd` can't read `/etc/shadow`, so the real password never unlocks.
- **Dependency audit:** `cargo-deny` and `cargo-audit`. Only known security advisories (and crates flagged unsound) fail it; licences, bans, duplicates and sources, configured in `deny.toml` at the repo root, only add a warning to the run for now.
- **Rust 1.98 (Ubuntu):** the same tests with exactly the declared `rust-version`, against Ubuntu's libpam and libxcrypt.

clippy and fmt are not in CI: run `just lint` before pushing. Results are in the repository's Actions tab, or through `gh run list` and `gh run view --log-failed`. Dependabot proposes weekly bumps for the pinned actions and for `Cargo.lock`, once the configuration is on `main`.

## Four things learned building it

- **The module must never be unloaded.** libpam `dlclose`s modules at every `pam_end`, but Rust's standard library registers thread-local destructors that glibc runs at thread exit. Once the module is unmapped, that segfaults the host process: here the lock screen (rust-lang/rust#91979). It reproduces on Fedora 44. The module is linked with `-z nodelete` (see `crates/pam/build.rs`), and the load/unload test in `tests/stack.rs` crashes without it.
- **A test that reads syslog must never stop reading.** A Unix datagram socket queues only a few messages (10 by default). The first container test read `/dev/log` between attempts only, so three concurrent attempts filled the queue, and the module, `pam_unix` and `unix_chkpwd` all blocked in `syslog()`, waiting for the test that was waiting for them. Logging from inside PAM is a blocking call, so a stalled syslog daemon could hang the lock screen the same way.
- **Setuid changes the user, not the group.** The first container run of the PIN checker failed every scenario: it ran as `screenlock-pin` but still had the caller's group, so it couldn't read hash files readable by the `screenlock-pin` group. The fix then was making it setuid and setgid; later the account was dropped altogether, and the PIN checker is now root-owned and setgid only, so the group is its whole identity. The local tests couldn't catch it, because there the caller owns everything; that is what the container is for.
- **`cargo test` doesn't relink the cdylib.** It rebuilds the module's rlib for the tests but leaves `target/debug/libpam_screenlock_pin.so` stale, so the stack tests build the module themselves before loading it.
