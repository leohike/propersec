# properpin plan

Improvements for properpin after the first Rust implementation. The installer and the container test came first, as the infrastructure; the code fixes follow. Nothing here deploys to the real machine; the "Touches the machine" column says what, if anything, lands outside the repo.

| Improvement | What | Why | Touches the machine | Effort | When |
|---|---|---|---|---|---|
| Close the repeated-access gap | Only a password unlock resets failures; a cap on total failures per boot; `status` shows both counts | Today a correct PIN wipes earlier failures, so someone with repeated access gets fresh guesses every time you step away; poc-py's security analysis puts a 4-digit PIN at about 1.4 years | No | Small, core plus property tests | Next, with a container scenario that walks the gap |
| A minimum duration for a PIN unlock | Pad a successful PIN check to about 100 ms, or raise the hash cost; test that a correct PIN never returns within 50 ms | kscreenlocker 6.8 reports any `pam_authenticate` within 50 ms as an unavailable service and marks it defunct; a correct PIN takes about 25 ms. See `docs/kscreenlocker-pam-contract.md` | No | Small | Before 6.8 reaches the real machine |
| Harness closer to kscreenlocker | Several attempts on one PAM handle, `pam_setcred` after a success, attempt processes checked for a clean exit, attempts killed midway | Both kscreenlocker versions reuse one handle, and 6.8 kills its PAM worker on cancel; see `docs/kscreenlocker-pam-contract.md` | No | Small to medium | With the minimum duration |
| Wipe secrets from memory | `zeroize` for the typed PIN and the copies made at the C boundary | Keeps PINs out of freed memory and core dumps; also practice for the FFI review checklist | No | Small | Next, with the gap |
| Install as code, tested against a fake root | One recipe with a `--root <dir>` option: module renamed to `pam_properpin.so`, CLI, `/etc/properpin` with owners and modes, the template's lines into `/etc/pam.d/kde` as a separate `enable`; `disable` takes out exactly those lines and never deletes the file | The real deployment becomes one command that has already been reviewed and tested; deleting `/etc/pam.d/kde` would lock everyone out | No | Medium | Done: `packaging/install.sh`, tested in `crates/systest/tests/install.rs` |
| SELinux labels | Write and document the labelling commands in the install recipe | Needed for the real install; cannot be verified without the real machine or a VM | No | Small to write, unverified | Written: `install.sh` relabels and `check` verifies when SELinux is enabled; unverified until a real machine or a VM |
| CI | GitHub Actions on every push and pull request: the tests in a Fedora 44 container, the podman system test on an Ubuntu runner, and the tests with exactly Rust 1.98; clippy and fmt stay local | A check that runs without anyone remembering to run it | No, runs on GitHub | Small | Done: `.github/workflows/ci.yml` |
| Dependency checks | `cargo-deny` and `cargo-audit` in CI: known advisories fail the run; licences, bans, duplicates and sources only warn for now | Third-party code runs inside the lock screen process | No, CI only | Small | Done in CI, configured in `deny.toml`; make licences, bans and sources fail once they have been looked at |
| Mutation testing | `cargo-mutants`: break the code on purpose and see whether the tests notice | The strongest single signal that the tests can be trusted without reading every line | Tool in `~/.cargo/bin`, or CI only | Small to run, ongoing to act on | With CI |
| Fuzz the settings parser | A fuzz target for `kv.rs` | The parser reads files and must never panic or accept garbage | Nightly toolchain, or CI only | Small | Later |
| Real-PAM test in podman | A Containerfile on Fedora 44 or the Aurora image; install with the install recipe into the container's real `/`; a test user with a real password; run `pamharness` as that user through the real `kde` stack, real `pam_unix` and `unix_chkpwd`; replay the scenarios from the poc-py rollout | Proves the real PAM file, real `pam_unix`, real libraries and the installed layout; the current stack tests swap `pam_unix` for `pam_permit` and `pam_deny` | Pulls images into the user's podman storage; never touches host PAM or `/etc` | Medium | Done: `just properpin podman`, 17 scenarios, checked by breaking things on purpose |
| systemd inside the podman test | Run the container with init so journald and logind run | `pam_syslog` lands in a real journal and logind creates `/run/user/<uid>` | Same as above | Small on top of podman | Optional |
| Incus container sandbox | A persistent system container with snapshots for poking at install, uninstall and breakage by hand | Convenience over podman, not extra coverage | Incus storage and network | Small | Optional |
| Incus VM rehearsal | A Fedora 44 KDE VM, later the real `aurora-pro` image via `bootc-image-builder`: real lock screen, SELinux enforcing, reboots, uninstall, snapshots | The only way short of the real machine to test kscreenlocker's own behaviour and SELinux | Incus storage and network | Large | Later, before each real install |
| Duress, TPM-backed counter, verifying daemon | Design first | Hardware-backed limits and a daemon that holds the hash | No, until built | Large | Not yet |
