## Deferred: the randomized kill test

**Why it came up.** Plasma 6.8 runs each unlock attempt in its own worker process and kills it (SIGTERM, then SIGKILL 25 ms later) whenever it cancels the attempt: the laptop going to sleep, a switch to fingerprint or smartcard, or the lock screen closing because something else unlocked the session. So properpin's module can die at any point inside an attempt.

**What is already covered, and how.** The security question was whether a well-timed kill can buy a free guess: a guess whose hash was checked but whose failure was never recorded. properpin records the failure before checking the hash, and takes it back on a match. Two unit tests in `crates/core/src/attempt.rs` pin that order down. `every_check_happens_with_its_attempt_already_counted` uses a hasher that records what the store holds at the moment it is asked, so the check can never run ahead of the count. `a_failure_is_saved_before_the_hash_is_checked` covers the case where the hash check fails outright. Moving the save below the hash check fails both, which has been checked on purpose. The per-boot total from the repeated-access fix gets the same treatment when it lands.

**Why not deterministic kill points.** The first idea was test-only hooks in the module, making it pause at named points so a test could kill it exactly there. Rejected: a hook placed right after the count is saved only confirms where it was put; the real property ("checked implies counted") is tested better and more simply by the unit tests above; and hooks would mean either test code in the shipped module or a second, test-only build. Nothing test-related goes into the shipped module.

**What the deferred test is for.** Not counting any more, but general stability and reliability under a hard kill, which needs the real kernel, files and processes rather than an in-memory store:

- **A readable state.** After a kill mid-write, the state file is either the old version or the new one, and always parses. The write goes through a temporary file and a rename, which should guarantee this.
- **The lock is released.** The next attempt gets the lock within its one-second timeout, because the kernel drops the lock with the dead process, and no attempt ever hangs.
- **A killed attempt has no effect.** It never unlocks, never arms the PIN, and never lowers or resets a count.
- **Leftover temporary files.** Stray `.properpin.*` files in `/run/user/<uid>` don't confuse later attempts. Count them, to decide whether the module should clean them up. The directory is cleared at logout either way.

**How, roughly.** In the container, start attempts as the test user (the PIN, wrong PINs, the password), kill each after a random delay between 0 and about 50 ms (spanning the whole module run, which is about 25 ms for a PIN check), with SIGTERM or SIGKILL, a few hundred times, and check the four points above after every kill. Then run normal attempts to confirm everything still works. There are no hooks: randomness finds the windows, including ones nobody thought of. Keep it under about 30 seconds, and offer a long opt-in run with thousands of kills.

**When.** After the repeated-access fix, because that changes what is written and when, and once the harness reuses a PAM session the way kscreenlocker does, so the kills land in a realistic lifecycle.
