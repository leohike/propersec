# Current concerns

What was still open on 2026-10-17, after the pepper was dropped and `install` became the one command that edits PAM, and since 2026-10-18, when `install` stopped editing PAM and `integrate-into-pam.sh` took that over, only when run. Most come from `docs/chaos/review-of-dropping-the-pepper.md`, which has the details; the last came out of the install change. Listed most serious first, each with the fix that seems right. The older, longer list is `docs/chaos/concerns.md`.

Fixed the same day: checks for absence that could pass while checking nothing. The container test's "no PIN checker left running" looked for a hardcoded process name that went stale at the rename to `screenlock-pin-checker`, so it found nothing, and passed, whatever was running. Its matchers, and those of the checks that another service or an uninstalled system logs nothing of screenlock-pin's, are now derived from the installed file names, and each check for absence has a positive control that finds its target in the same run; the PAM stack test's "no PIN unpause after a wrong password", which only matched the module's error, now matches the PIN unpause's own answers. Breaking each matcher on purpose failed the scenario it guards.

The first concern listed that day, state in `/var/lib/screenlock-pin` that nothing ever cleared, was fixed the same day too: `set` creates the lock file and the budget and the PIN checker never creates either, so neither can be planted; a write clears the temporary files that killed writes left; a refused attempt writes only what judging changed; and `enable` and `remove` take the lock.

Also fixed that day: one badly moded user file turned the PIN off for everyone, since `install` ran the full check, user files included, before putting screenlock-pin's lines back. A problem with a user's file, budget or lock file refuses that user's PIN alone, at the PIN checker, so `install` and `check` no longer judge them, nor the config: `install` puts its lines in anyway and ends by printing what the new `sudo screenlock-pin doctor` finds. Doctor judges every file by the PIN checker's own rules, as root, so those rules now also cover what only root could meet, a file the PIN checker couldn't read at all, and a user file must have the PIN checker's group; for each problem doctor says what it does at the lock screen and which command fixes it. There are no repairs, only `remove` (whatever state the files are in, by name for an account that is gone, or `--all` for every user), `set`, `enable`, `restore-defaults`, which deletes the config, and installing again. `status` says why a PIN is refused instead of sending the user to the system log, and install no longer deletes the PINs and budgets of versions with a pepper: doctor names them.

## The tests can be trusted a little less

- The confirmation prompt on a real terminal, `y` and `N`, is untested, in `screenlock-pin` and in `integrate-into-pam.sh` alike.
- Mutation testing hasn't been run on the new code.

The fix: drive the prompts through a pseudo-terminal in the CLI tests; a run of `just mutants`, working through what survives.

## faillock doesn't stop the PIN

Since 2026-10-18 every input the `check` line doesn't accept goes through the stock `password-auth` stack, so with authselect's `with-faillock` on (it is off on stock Fedora) a wrong PIN counts towards faillock's lockout like a wrong password, as it should. One gap remains, only with faillock on: while faillock has the account locked, a right PIN still unlocks, since the `check` line runs before the substack that holds faillock. The other gap, a right password unpausing the PIN while faillock has the account locked, is gone since the PIN unpause moved to `pam_setcred` (docs/current-setcred.md): the stock stack fails, so the lock screen never calls `pam_setcred`. Reasoned, not yet tested with faillock on.

The fix, deferred: have the PIN checker refuse the PIN while faillock has the account locked, asking faillock the way `pam_faillock preauth` does.

## integrate-into-pam.sh edits any PAM file with the one stock line

Until 2026-10-18 `install` edited `/etc/pam.d/kde` itself, with a `pam_unix` line of its own that assumed the password check is plain `pam_unix`: on a machine that authenticates through sssd it would have refused the right password and locked the lock screen. Now `install` never touches PAM, the `pam_unix` line is gone, and screenlock-pin's two lines sit around the stock stack without changing what it decides, so that lock-out can't happen. `integrate-into-pam.sh add`, which only runs when asked, still edits any file with exactly one `auth substack password-auth` line, whatever is around it or behind it. What is left for a user whose password `unix_chkpwd` can't check (sssd, systemd-homed): the PIN unpause never finds their password right, so a paused PIN stays paused for them.

The fix, deferred: have `add` say so when the auth lines aren't Fedora's stock pair, or the profile behind them isn't authselect's plain local one, and have the README say plainly what screenlock-pin was tested with.

## Considered and dismissed

- **Anything an administrator does to a user's PIN.** Since the pepper went, `set` needs only root, so `sudo screenlock-pin set --user bob` gives bob a PIN the administrator chose and knows, without bob's password; root can also skip the comparison with `--shadow /dev/null`, lower `hash_cost` to 1, or re-run `enable` until the total limit. None of it is a concern: root can already unlock bob's session outright with `loginctl unlock-session`, change his password, or install a PAM module of its own, and the threat table in `docs/chaos/security-target.md` says root wins either way. Dismissed on 2026-10-17, together with the entries in `docs/chaos/concerns.md` and `docs/chaos/review-of-dropping-the-pepper.md` that only root could cause.
- **The PIN-equals-password check is narrow.** It runs only at `set`, catches an exact match only, and is skipped for users without an entry in `/etc/shadow` (LDAP, systemd-homed), so a password changed to the PIN later goes unnoticed. That is the user's own choice, and `set` says to keep the PIN different from all account passwords. The PIN unpause couldn't warn about it anyway: a password equal to the PIN is taken as the PIN, so the PIN unpause never runs. `docs/chaos/why-pin-same-as-password-bad.md` has what it costs. Dismissed on 2026-10-17.
- **Moving the clock to stretch the budget.** Setting the time takes root or admin authentication; a reboot ends at the LUKS passphrase, and even with TPM unlock at the login screen, where the PIN doesn't apply; a forged NTP answer from the network can only step the clock in chrony's first updates after start, that is after a reboot, and otherwise slews it by at most about 0.08 seconds a second. And the limit of 60 per PIN doesn't depend on time at all, so clock games could at best bring those guesses sooner. So `judge` no longer treats a failure stamped in the future as proof that the clock went back (`CLOCK_SLACK`, removed on 2026-10-17 with its test): after an honest jump back, such failures just wait for the clock to catch up, and the next password unlock may forgive them as the user's own. The property test lost its reboot event when the PIN started working from boot on, since nothing in the code knows about boots any more.
