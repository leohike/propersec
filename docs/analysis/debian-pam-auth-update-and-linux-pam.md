# Debian pam-auth-update and linux-pam semantics, for screenlock-pin

A read-only investigation of how distributions let a package add itself to PAM stacks (Debian's pam-auth-update above all, with Fedora's authselect for comparison), and of the linux-pam semantics that decide whether screenlock-pin's three lines could live in a file of screenlock-pin's own. Everything cited is from the reference clones under /var/home/shared/projects/pam-related/ (paths below are relative to that directory unless they start with `/`), from this repository, or from the running Fedora 44 / Aurora host. Each claim is tagged **Verified** (read in code or on the host) or **Inferred** (reasoned from verified facts, or from general knowledge not present in the clones).

## Summary and recommendation

- pam-auth-update only ever writes the five files `/etc/pam.d/common-{auth,account,password,session,session-noninteractive}`. It never touches a per-service file such as `/etc/pam.d/kde`. Anything screenlock-pin registered through it would land in `common-auth`, which on Debian is pulled in by login, sshd, sudo, su, polkit and the `other` fallback alike. **Verified** for the file list; **Inferred** for the list of consumers beyond `other`.
- screenlock-pin could only use pam-auth-update by gating its lines on `pam_succeed_if.so service in kde`. That is technically expressible, but it would `dlopen` pam_screenlock_pin.so into sudo, sshd, login and every other process that reads `common-auth`. It would also make one string comparison the only thing that keeps the PIN out of sudo. That breaks screenlock-pin's lock-screen-only scope in spirit and in attack surface, so I do not recommend it.
- `auth include screenlock-pin` (screenlock-pin's three lines moved into `/etc/pam.d/screenlock-pin`) builds exactly the same handler list as today's inline block, so it behaves identically at run time. **Verified** in `libpam/pam_handlers.c`.
- `auth substack screenlock-pin` does **not** behave the same. `done` would end only the substack, so after a correct PIN the stock `password-auth` substack would check the PIN as a password and `pam_deny` would fail the unlock. PIN unlock would never work, although it fails closed.
- Every kind of include adds one failure mode that the inline block does not have. If the included file is missing, unreadable by the user the greeter runs as, or fails to parse, libpam installs a must-fail handler in its place, and the whole lock screen refuses even the correct password: a lockout. A missing pam_screenlock_pin.so in today's inline block is harmless by comparison, because the module line turns into `PAM_MODULE_UNKNOWN` and is ignored. The `-` prefix does not soften a missing include. **Verified**.
- Recommendation: keep today's marked inline block for Fedora and Aurora. The benefits of a one-line include (a smaller diff in `/etc/pam.d/kde`, and updates that don't touch that file) are real but small, and they cost a new lockout path. For other distributions, use the same marked-block edit through screenlock-pin's own installer or command, explicitly run by the admin. Do not use a distro-level PAM manager (pam-auth-update, authselect), and do not edit another package's PAM file from a package maintainer script.
- Portability caveat, independent of the mechanism: the second line hard-codes `pam_unix.so … default=die`. On a host where the user is not in `/etc/shadow` (SSSD, LDAP, AD, Kerberos), that line would refuse the correct network password at the lock screen. **Inferred**. Other distributions will need a different second line, or a guard.
- Bonus: linux-pam has nothing PIN-like. pam_tally/pam_tally2 are gone (removed in 1.5.0). pam_faillock is the closest analogue, but its tally files are owned by the user and kept on tmpfs. It cannot even create its tally when run from the unprivileged kscreenlocker greeter, and then silently passes. screenlock-pin's setgid PIN checker with a group-owned budget under `/var/lib/screenlock-pin` is strictly stronger for this threat model. pam_faildelay and pam_fail_delay are under the application's control, so they are no defence against brute force.

## How screenlock-pin hooks in today

- `packaging/kde-auth.pam:20-22` holds the three lines: `auth [success=done default=ignore] …pam_screenlock_pin.so check …`, `auth [success=ok default=die] pam_unix.so use_first_pass`, and `auth optional …pam_screenlock_pin.so housekeeping …`. **Verified**.
- `packaging/install.sh:93-106` targets `/etc/pam.d/kde` and saves a backup to `/etc/screenlock-pin/kde.pam.without-screenlock-pin`. The markers are `# screenlock-pin begin: …` and `# screenlock-pin end`, and the anchor regex is `^auth\s+substack\s+password-auth`. `add_block` (install.sh:224-227) prints the block above the first anchor line. `remove_block` (install.sh:229-231) deletes everything from the begin marker to the end marker. `do_install` (install.sh:378-389) refuses unless there is exactly one anchor and the change is exactly reversible. It shows a diff and asks before writing. **Verified**.
- The module reads the typed secret through `pam_get_authtok(PAM_AUTHTOK)` (`crates/pam/src/pam.rs:163`), so libpam stores it as `PAM_AUTHTOK` for the rest of the stack (`crates/pam/src/run.rs:23-26`). Its `pam_sm_setcred` returns `PAM_IGNORE` (`crates/pam/src/pam.rs:74-76`). **Verified**. Both facts matter for the substack analysis below.
- kscreenlocker uses the PAM service named by the CMake cache variable `KSCREENLOCKER_PAM_SERVICE`, which defaults to `kde` (`kscreenlocker/CMakeLists.txt:86-95`). It uses separate `kde-fingerprint` and `kde-smartcard` services for the other authenticators (`kscreenlocker/greeter/worker/CMakeLists.txt:29-30`). It calls `pam_start(service, user, …)` (`greeter/worker/main.cpp:265`), installs its own `PAM_FAIL_DELAY` callback (main.cpp:275-276), and calls `pam_authenticate` (main.cpp:311) and then `pam_setcred(PAM_REFRESH_CRED)` on success (main.cpp:317). **Verified**.
- On the host, `/etc/pam.d/kde` belongs to `plasma-workspace` and is flagged `%config(noreplace)` (`rpm -q --qf '[%{FILENAMES} %{FILEFLAGS:fflags}\n]' plasma-workspace` prints `cn`). The ostree image copy `/usr/etc/pam.d/kde` is currently byte-identical to `/etc/pam.d/kde`. **Verified**. Any local edit, whether inline block or include line, therefore means: on rpm-based Fedora, a future change to the shipped file arrives as `/etc/pam.d/kde.rpmnew` and is not applied. On Aurora, the ostree three-way `/etc` merge keeps the locally modified file and ignores later image changes to it. **Inferred** from standard rpm and ostree behaviour. The size of screenlock-pin's edit does not change this; it only changes how hard a manual merge is.

## Debian pam-auth-update

### What it is and which files it manages

- It is a Perl script, `debian-pam/debian/local/pam-auth-update`, described on line 3 as "update /etc/pam.d/common-* from /usr/share/pam-configs". It reads every profile in `$inputdir = '/usr/share/pam-configs'` (line 34, read at lines 112-120). It writes into `$confdir = '/etc/pam.d'` (line 40) and keeps its state in `$savedir = '/var/lib/pam'` (line 41). **Verified**.
- `write_profiles` (lines 479-586) loops over exactly `'auth','account','password','session','session-noninteractive'` (lines 490-491). Its target is `$confdir . '/common-' . $type` (line 493). It writes `common-X.pam-new` and renames it over the target (lines 495 and 576-577). `diff_profiles` reads the same five files (lines 604-605 and 632). No other path under `/etc/pam.d` appears anywhere in the script. **Verified**: pam-auth-update never touches a per-service file such as `/etc/pam.d/kde`, `/etc/pam.d/sddm` or `/etc/pam.d/sudo`.
- The man page states the same scope. FILES lists only `/etc/pam.d/common-*`, "Global configuration of PAM, affecting all installed services" (`debian/local/pam-auth-update.8:96-101`). **Verified**.
- The templates ship as `/usr/share/pam/common-*` (`debian/libpam-runtime.install:3`). The live `/etc/pam.d/common-*` files are generated by the postinst, not shipped in `/etc`, so they are **not** dpkg conffiles. **Verified**. This is deliberate: a script may rewrite them freely. By contrast, `/etc/pam.d/other` is installed into `etc/pam.d` (`libpam-runtime.install:2`) and is therefore a conffile (**Inferred** from debhelper's automatic conffile marking of `/etc`). The 2003 changelog records the back-and-forth: "Make other a conffile again and update to @include stuff" (`debian/changelog`, the pam 0.76-14 entry, around line 2162).

### Profile format

A profile is a pseudo-RFC822 file parsed by `parse_pam_profile` (lines 709-746). Fields are `Name:` lines. Continuation lines are indented, and they are trimmed and joined with newlines (lines 716-737). The fields the script actually uses:

- `Name` is the label in the debconf checklist (line 136).
- `Default: yes|no`. A profile not yet "seen" with `Default: yes` is enabled automatically (lines 178-180). "Seen" profiles are recorded in `/var/lib/pam/seen` (lines 147-155 and 260-264). **Verified**.
- `Priority` is a number. Profiles are sorted by descending Priority, then by name in reverse (lines 128-130 and 181-183). That order is the order of lines in each block. For example, Debian's `unix` profile has 256 (`debian/pam-configs/unix:3`) and howdy has 512 (`howdy/howdy/src/pam-config/howdy.in:3`), so howdy goes first. **Verified**.
- `Conflicts: a, b`. For each conflicting pair, the lower-priority profile is unset and the user is warned through the `libpam-runtime/conflicts` template (lines 229-247). **Verified**.
- `Auth-Type`, `Account-Type`, `Password-Type`, `Session-Type` take `Primary` or `Additional`. They decide which block of the template a profile's lines go into (lines 375-378 and 400-401). **Verified**.
- `Auth`, `Account`, `Password` and `Session` hold the lines. `Auth-Initial` (and the like) is used instead when the profile is the first in its block (`lines_for_module_and_type`, lines 320-327). Debian's `unix` profile uses this so that pam_unix gets `try_first_pass` only when it is not first (`debian/pam-configs/unix:5-8`). `Auth-Final` is an old spelling, silently renamed to `Auth` (line 720). **Verified**.
- `Session-Interactive-Only: yes` keeps the session lines out of `common-session-noninteractive` (lines 740-744). **Verified**.
- Any profile containing `pam_tally` is marked `disabled` and dropped (lines 66, 733-735 and 116-118), which follows pam_tally's removal upstream. **Verified**.

### How the managed block is built

- The template `debian/local/common-auth:16-26` contains the marker comment `# here are the per-package modules (the "Primary" block)`, then `$auth_primary`, then `# here's the fallback if no module succeeds`, then `auth requisite pam_deny.so` and `auth required pam_permit.so`, then `# and here are more per-package modules (the "Additional" block)`, then `$auth_additional`, and finally `# end of pam-auth-update config`. **Verified**.
- `create_from_template` (lines 331-421) copies the template and replaces the parts between those marker comments with the enabled profiles' lines. In each line, the word `end` in the control field is replaced by the number of lines remaining in the block, so that `[success=end default=ignore]` jumps exactly past `pam_deny` onto `pam_permit` (`merge_one_line`, lines 293-297; counting at lines 372-387 and 403-408). In the Additional block the count is one lower, "so we don't jump off the stack" (lines 385-387). If no Primary profile is enabled, a `[default=1] pam_permit.so` line is written instead (lines 391-394). **Verified**.
- The semantics that follow from this are: **Primary** modules are alternatives. The first one to succeed jumps to `pam_permit`. If none succeeds, `requisite pam_deny` stops the stack. **Additional** modules run only after some Primary module has succeeded, because `pam_deny` is requisite, and they typically carry `optional`. **Verified** from the template and the jump rewriting.

### State, the "local modifications" refusal and the md5 checks

Two separate mechanisms are often lumped together as "the md5 check".

- **Detecting edits inside the managed block.** `diff_profiles` (lines 593-705) loads `/var/lib/pam/<type>` (the lines it wrote last time, tagged `Module: <profile>`) and walks the live `common-<type>` between the markers. Option changes to known lines are remembered as add/remove sets and preserved on the next write (lines 685-697, applied in `merge_one_line` lines 298-316). But "there's a line in the live config that doesn't correspond to anything from the saved config. treat this as a failure" (lines 678-683). The same goes for a missing marker or a missing saved state (lines 609 and 701-702). When `diff_profiles` fails and `--force` was not given, the script asks the debconf `libpam-runtime/override` question at high priority (lines 198-202). If the answer is no, it prints "Local modifications to /etc/pam.d/common-*, not updating." and exits without writing (lines 204-212). The man page says the same (pam-auth-update.8:51-59). **Verified**.
- **Detecting edits outside the managed block.** `get_template_md5sum` (lines 426-475) hashes the live file with the managed blocks cut out and compares the result with the known pristine hashes in `%md5sums` (lines 46-65). If they match, the next file is generated from the pristine `/usr/share/pam/common-<type>`. Otherwise the admin's own file is used as the template, so edits outside the block survive (lines 502-511). Only when that fails *and* `--force` was given does it fall back to the pristine template (lines 514-526). With `--force`, the old file is kept as `common-<type>.pam-old` (lines 572-575). **Verified**.
- **The postinst's md5 check** is different again. `debian/libpam-runtime.postinst:7-31` hashes the parts outside the block with `sed` and looks the result up in `/usr/share/pam/<file>.md5sums`. Only on a first install (`[ -z "$2" ]`, line 19) and only when every file is pristine does it pass `--force` (line 33). It then deletes the `.pam-old` copies (lines 35-40). **Verified**.
- In short, pam-auth-update merges edits outside its markers, keeps option tweaks to its own lines, and refuses to proceed if anyone added a line inside its block, unless the admin overrides. **Verified**.

### Package integration: --package, --remove, --force

- `--package` lowers the debconf priority to `medium`, so a package install doesn't prompt by default (line 122; man page lines 70-73). **Verified**.
- `--remove p…` drops those profiles from the selection and implies `--package` (lines 88-94 and 132). The man page says it "should be used to remove profiles from the configuration before the modules they reference are removed from disk, to ensure that PAM is in a consistent and usable state at all times" (pam-auth-update.8:82-88). The idiom is shown, commented out, in `debian/libpam-runtime.prerm:16-18`: `if [ "$1" = remove ] ; then pam-auth-update --package --remove <profile>; fi`. **Verified**.
- `--force` "**must not** be used by package maintainer scripts; it is intended for use by administrators only" (man page lines 90-95). The script comment calls it a matter for "big skullses and crossboneses" (lines 68-75). **Verified**.
- `--enable` and `--disable` are for admin scripts (lines 95-109). **Verified**.
- A third-party example: howdy's Debian `postinst` just runs `pam-auth-update --package` (`howdy/howdy/debian/postinst:205-206`). Its `prerm` runs it, deletes `/usr/share/pam-configs/howdy`, and runs it again (`howdy/howdy/debian/prerm`, the "Refresh and remove howdy from pam-config" block), rather than using `--remove`. Its profile is `Auth-Type: Primary`, `[success=end default=ignore] pam_howdy.so`, at Priority 512 (`howdy/howdy/src/pam-config/howdy.in:1-6`). **Verified**. This shows the default outcome of using pam-auth-update: face recognition becomes sufficient for **every** service that includes common-auth, sudo and ssh included.

### Could screenlock-pin use pam-auth-update and stay lock-screen-only?

Not cleanly, and I recommend against it. The reasoning:

- pam-auth-update has no per-service field. The only fields it uses are listed above, and none names a service. Its output is the global `common-auth`. **Verified**.
- Debian's PAM mini-policy tells every service file to `@include common-auth` and its siblings (`debian/local/Debian-PAM-MiniPolicy:23-29`). `/etc/pam.d/other` does too (`debian/local/other:13-16`). So anything in `common-auth` reaches every service that follows the policy. **Verified** for the policy and for `other`; **Inferred** for each specific service (sudo, sshd, login, polkit-1 and sddm are not in the clones).
- The only way to restrict it is a gate inside the profile, the way authselect does for smartcards: `auth [success=1 default=ignore] pam_succeed_if.so service notin login:gdm:xdm:kdm:kde:xscreensaver:gnome-screensaver:kscreensaver quiet use_uid` (`authselect/src/man/authselect-profiles.5.adoc:188`). linux-pam's pam_succeed_if does support the `service` field (`linux-pam/modules/pam_succeed_if/pam_succeed_if.c:328-331`). A screenlock-pin profile could look like `Auth-Type: Primary`, `Priority` above 256, with `Auth:` set to `[success=1 default=ignore] pam_succeed_if.so service notin kde quiet` followed by `[success=end default=ignore] /…/pam_screenlock_pin.so check …`. The `after-password-auth` line would go in an `Additional` profile, gated the same way. Debian's `unix` profile, now non-initial, gets `try_first_pass` and so reuses the typed secret. Numeric jumps inside a profile are left alone by `merge_one_line`, which only rewrites the word `end` (line 297). **Inferred**: I have not run it.
- Why it is still wrong for screenlock-pin:
  - **Attack surface.** libpam loads every module named in the parsed stack when it builds the handlers, before any line runs (`linux-pam/libpam/pam_handlers.c:721-740` calls `_pam_load_module` → `_pam_dlopen` at parse time, lines 642-645). A gated pam_screenlock_pin.so would therefore be mapped into setuid sudo, su, sshd, login and polkit-agent-helper on every authentication, with its initialisers and dependencies, even though it never runs there. **Verified** that loading happens at parse time; the specific consumers are **Inferred**.
  - **One string compare as the only barrier.** If the gate line is lost or mistyped by a later admin edit, or reordered by a future pam-auth-update change, the PIN silently becomes valid for sudo and ssh. That is the scope screenlock-pin promises not to have.
  - **Semantics differ from today.** Debian's Primary block has no "wrong password stops here" line. screenlock-pin's line 2 (`default=die`) has no place in a shared block, where SSSD, krb5 and similar Primary modules may follow. The pause-until-password logic would need to be re-verified against arbitrary other profiles, which can be added later by any package.
  - **Admin UX.** The profile shows up in a debconf checklist for the whole system's "central authentication policy" (man page lines 30-34), described as something like "PIN for the KDE lock screen". Unticking it disables it everywhere. That part is fine, but it invites people to believe it is a system-wide login method.
- Conclusion: pam-auth-update is the right tool for a module meant to be part of the *system* authentication policy (pam_unix, sss, krb5, howdy). It is the wrong tool for a module that must be confined to one service. **Inferred**, but it follows directly from the verified facts above.

### Debian's own per-service files for KDE

- None of the clones contains Debian's `/etc/pam.d/kde`, `/etc/pam.d/sddm` or `/etc/pam.d/kscreensaver`. `grep -rli 'kscreensaver\|pam.d/kde\|sddm'` over `debian-pam` finds nothing. **Verified**: they would come from the sddm and kscreenlocker Debian packages, which are not cloned.
- What can be stated: Debian's `other` is permissive in the sense that it `@include`s `common-auth`, `common-account`, `common-password` and `common-session` (`debian/local/other:10-16`). Fedora's `/etc/pam.d/other` is `pam_deny` for all four types (host file). So the warning in `packaging/install.sh:32-34`, that deleting `/etc/pam.d/kde` "would hand the lock screen to the 'other' service, which denies everyone", holds on Fedora but not on Debian. There the lock screen would fall back to common-auth and the password would still work. **Verified** for both `other` files.
- **Inferred, to check on a real Debian or Kubuntu host**: whether Debian's kscreenlocker ships a `kde` service file at all, or relies on `other`. If it relies on `other`, screenlock-pin creating `/etc/pam.d/kde` would turn it into a real service file. It would then need the full four-type content (`@include common-*`) as well as screenlock-pin's lines, and the "anchor line" would be `@include common-auth`, not `auth substack password-auth`.

### Debian guidance on packages editing other packages' PAM files

- The mini-policy (`debian/local/Debian-PAM-MiniPolicy`) states that each application "must contain a file in /etc/pam.d/" (lines 23-29), that service-specific modules belong in "the service's /etc/pam.d file" (lines 41-43), that modules should be named by basename rather than full path (lines 71-74), that packages using modules beyond common-* must depend on the providing package (lines 77-84), and that module config belongs in `/etc/security/<name>.conf` (lines 144-145). It says nothing about one package editing another package's `/etc/pam.d` file. **Verified**.
- Debian Policy proper (not in the clones) forbids a package's maintainer scripts from modifying another package's conffiles. `/etc/pam.d/<service>` files are conffiles of their owners. **Inferred** from general knowledge of Debian Policy's section on configuration files. This is the reason pam-auth-update exists, and why `common-*` are generated non-conffiles (see "What it is and which files it manages" above). For screenlock-pin on Debian, it means a .deb must not edit `/etc/pam.d/kde` in its postinst. The edit has to be an admin action, such as screenlock-pin's own installer or command run by the admin, or documented manual steps.
- screenlock-pin's full-path module names (`/usr/local/lib64/security/pam_screenlock_pin.so`) go against the mini-policy's "basename" advice (lines 71-74). That is fine for a locally installed tool, but a distro package would put the module in the distro's module directory and use the basename. **Verified** for the advice; the rest is a judgement.

### Debian and /usr/lib/pam.d

- Upstream libpam reads `/usr/lib/pam.d` unconditionally (see "Where libpam looks for a service file" below). Debian's maintainer says "it was never my intent to support /usr/lib/pam.d on Debian" (`debian/changelog`, 1.7.0-6, lines 48-53). In 1.7.0-7 Debian stopped documenting it (changelog lines 13-16; patch `debian/patches/0025-By-default-do-not-document-usr-lib-pam.d.patch` adds a `usrlibpamd` meson option, `disabled` by default, which only changes the docs). A patch that would log an error whenever a file is found there (`0024-Warn-when-usr-lib-pam.d-is-used.patch`) exists but is **not** listed in `debian/patches/series`. **Verified**. So on Debian, `/usr/lib/pam.d` still works in code, but it is officially unsupported and may start logging errors. A Debian package of screenlock-pin should not rely on it.
- `@include` is a Debian-only patch (`debian/patches/031_pam_include`), "Upstream status: not yet submitted". When the *type* column is `@include`, it sets `module_type = requested_module_type` and jumps straight to reading the file name, so `@include common-auth` includes **every** type from that file at the same stack level (no substack). Upstream linux-pam has no `@include`: `grep '@include' linux-pam/libpam/*.c` finds nothing. **Verified**. A file using `@include` is therefore not portable to Fedora, Arch or SUSE. Per type, `@include X` behaves like `TYPE include X`.
- Debian also carries `045_pam_dispatch_jump_is_ignore`, which makes a jump count as `ignore` even when the frozen setcred or close_session chain is replayed. Upstream instead treats it as `required` there (`linux-pam/libpam/pam_dispatch.c:262-278`). screenlock-pin's lines contain no jumps, so this does not matter for them. **Verified**.

## Fedora's counterpart, authselect

- authselect writes only `system-auth`, `password-auth`, `fingerprint-auth`, `smartcard-auth`, `switchable-auth`, `postlogin` (plus nsswitch.conf and dconf) (`authselect/src/lib/paths.h:37-45`). On the host, `/etc/pam.d/{password-auth,system-auth,…}` are symlinks into `/etc/authselect/`. **Verified**. Like pam-auth-update, it never writes a per-service file such as `/etc/pam.d/kde`, and a custom authselect profile would put screenlock-pin into `password-auth`. On the host, that is substacked by `kde`, `plasmalogin` (`/usr/lib/pam.d/plasmalogin`) and others, and included by `sshd` on stock Fedora (**Inferred** for sshd). The same objections apply as for pam-auth-update.

## Where libpam looks for a service file

- `pam_private.h:28-35` defines `/etc/pam.conf`, `/etc/pam.d/%s`, `/usr/lib/pam.d/%s`, and `VENDORDIR"/pam.d/%s"` when the build sets a vendordir. **Verified**.
- `_pam_open_config_file` (`pam_handlers.c:293-352`) tries, in order, an absolute path when the name starts with `/` (lines 308-313), or `pamh->confdir` when the application set one with `pam_start_confdir` (lines 314-319). Otherwise it tries `/etc/pam.d/X`, then `/usr/lib/pam.d/X`, then `VENDORDIR/pam.d/X` (lines 298-302 and 333-349). It takes **the first file that opens** and reads only that file (lines 343-347). Precedence is per file name: an `/etc/pam.d/kde` completely hides `/usr/lib/pam.d/kde`. Nothing is merged, and there are no drop-in directories. The docs agree: "If no machine configuration file is found, the vendor-supplied file is used. All files in /etc/pam.d/ override files with the same name in other directories" (`doc/man/pam.conf-dir.xml:11-18`; `pam.conf.5.xml:46-66`). **Verified**.
- The same function resolves `include` and `substack` targets (`_pam_load_conf_file`, lines 354-402, calls it with the target name). An include line can therefore name an absolute path, or a bare name that is looked up in `/etc/pam.d`, then `/usr/lib/pam.d`, then vendordir. **Verified**.
- The `/usr/lib/pam.d` fallback has existed since 1.2.0 (`NEWS:266`). Vendordir became enabled by default in upstream's build in 1.7.2 (`NEWS:34`; `meson_options.txt:90` defaults it to `/usr/share/pam`). **Verified**.
- On the host, `strings /usr/lib64/libpam.so.0` contains `/etc/pam.d/%s` and `/usr/lib/pam.d/%s` and nothing under `/usr/share/pam`. So Fedora 44's libpam searches `/etc/pam.d`, then `/usr/lib/pam.d`, with no vendordir. Oddly, the `%_pam_vendordir` rpm macro says `/usr/share/pam.d` (`/usr/lib/rpm/macros.d/macros.pam`). `/usr/lib/pam.d` is in real use on the host: plasmalogin, polkit-1, systemd-run0 and systemd-user ship their service files there. **Verified**.
- If the service file is missing, `_pam_init_handlers` still parses `other` (lines 496-546). For each function, dispatch uses `other`'s handlers when the service has none for that type (`pam_dispatch.c:383-405`). If nothing at all could be read, the result is `PAM_ABORT` (lines 543-545). **Verified**.
- Since `/etc/pam.d/kde` is an `/etc` file owned by plasma-workspace on Fedora, a screenlock-pin-owned `/usr/lib/pam.d/kde` would simply be hidden by it. Shipping screenlock-pin's *own* include target in `/usr/lib/pam.d` would work on Fedora, but on Aurora `/usr` is the read-only image, so only a layered or image-built RPM could put it there. screenlock-pin installs under `/usr/local`, which is writable. **Inferred** from the lookup order and the host layout.

## include, substack and @include

### Parse time (`libpam/pam_handlers.c`)

- `include` sets `pam_include = 1, substack = 0`. `substack` sets `pam_include = 1, substack = 1` (lines 185-192). Neither takes a control clause: the control field *is* the keyword, so `actions[]` stays `_PAM_ACTION_UNDEF` (reset at lines 150-154). **Verified**. This confirms the comment in `kde-auth.pam` that "a substack can't take a control clause".
- For `substack`, a placeholder handler of type `PAM_HT_SUBSTACK` is added at the *current* `stack_level` (lines 202-211). Then, for both, the target file is parsed with `include_level + 1` and **`stack_level + substack`** (lines 212-218). For `include`, the included lines are therefore added at the **same** stack level as the including file, and no handler is added for the include line itself (`continue` at line 218). For `substack`, they are added one level deeper, after a placeholder. **Verified**.
- Only lines of the requested type are taken from the included file. `auth include X` reads only X's `auth` lines (lines 141-146, `requested_module_type`). **Verified**.
- The nesting limit is `PAM_SUBSTACK_MAX_LEVEL` = 16 (`pam_private.h:208`, checked at `pam_handlers.c:370-374`). **Verified**.
- **A missing or unreadable target.** If `_pam_load_conf_file` fails, which covers both "unable to open config" (lines 394-399) and a read error, the include line itself becomes a handler with `handler_type = PAM_HT_MUST_FAIL`, `mod_path = NULL`, and every action set to `_PAM_ACTION_BAD` (lines 219-222, then added at lines 278-280). **Verified**.
- The `-` prefix (`-auth include X`) sets `PAM_HT_SILENT_MODULE` (lines 118-120), but the failure path above overwrites the handler type with `PAM_HT_MUST_FAIL` (line 221). The prefix only affects missing *modules* (lines 666-668 and 682-683), not missing include targets. **Verified**.
- **A missing module** (contrast). `_pam_load_module` adds a "faulty module" entry with `dl_handle = NULL` (lines 678-685). The handler gets `func = NULL` and keeps its line's own actions. **Verified**.

### Run time (`libpam/pam_dispatch.c`)

- The handler list for a function is walked once (lines 79-307). The `PAM_HT_SUBSTACK` placeholder is skipped (lines 99-101). A `PAM_HT_MUST_FAIL` handler yields `PAM_PERM_DENIED` (lines 96-98, with `PAM_MUST_FAIL_CODE` defined at line 17). A handler with `func == NULL` (a missing module) yields `PAM_MODULE_UNKNOWN` (lines 102-104). **Verified**.
- `ok` and `done` (lines 208-229): if the stack has no verdict yet, or is positive with `PAM_SUCCESS`, the stack becomes positive with this return code. `done` then jumps to `decision_made` only if the stack is positive. **Verified**.
- `bad` and `die` (lines 231-251): if the stack isn't already negative, it becomes negative with this code (`PAM_IGNORE` is turned into `PAM_PERM_DENIED`). `die` then jumps to `decision_made`. **Verified**.
- `decision_made` (lines 302-306) skips every following handler **whose `stack_level >= ` the current level**, then the loop *continues*. In the outermost stack (level 0) that skips everything. Inside a substack (level ≥ 1) it skips only the rest of that substack and its nested children. Evaluation then resumes at the next handler of the parent level. **Verified**. This is exactly what the man page says: "evaluation of the done and die actions in a substack does not cause skipping the rest of the complete module stack, but only of the substack" (`doc/man/pam.conf-syntax.xml:187-203`).
- There is no separate "result of the substack" step. The substack's lines update the same `impression` and `status` as the parent. When a substack is entered, its starting state is saved (lines 89-93), but that is used only by `reset` (lines 202-206). Jumps never leave the level they are in (lines 280-287), and a whole substack counts as one module for a jump in the parent. **Verified**.
- `optional` means `success=ok new_authtok_reqd=ok default=ignore` (`pam_handlers.c:175-179`). `required` and `requisite` default to `bad` and `die` respectively (lines 163-174). A bracketed control defaults every unnamed code to `bad` (lines 193-197). **Verified**.
- For the setcred replay (`use_cached_chain`), the auth chain's cached return codes decide which action applies (lines 140-195). Since `include` produces the same handler list as inline lines, the replay is also the same. **Verified** by construction.

## Would screenlock-pin's lines behave the same from /etc/pam.d/screenlock-pin?

The hypothetical:

```
# /etc/pam.d/screenlock-pin  (auth lines only are read through the include)
auth  [success=done default=ignore]  /usr/local/lib64/security/pam_screenlock_pin.so check …
auth  [success=ok default=die]       pam_unix.so use_first_pass
auth  optional                       /usr/local/lib64/security/pam_screenlock_pin.so housekeeping …

# /etc/pam.d/kde, instead of the three lines
auth        include       screenlock-pin      (or: substack screenlock-pin)
auth        substack      password-auth
auth        include       postlogin
…
```

### With `auth include screenlock-pin`: identical

- The three handlers are added at level 0, in the same position and with the same actions, module paths and arguments as the inline block. The include line adds no handler of its own (`pam_handlers.c:212-218`). The run-time walk is therefore indistinguishable for `pam_authenticate`, and for `pam_setcred` too, which kscreenlocker calls with `PAM_REFRESH_CRED` after success (`main.cpp:317`). **Verified**.
- The only differences are outside the run-time logic: the include-time failure mode (below), the file's permissions and SELinux label, and the fact that `/etc/pam.d/screenlock-pin` is also a valid *service* name (below).

### With `auth substack screenlock-pin`: not identical

Handlers: `[SUBSTACK placeholder, L0]`, then PIN, unix and PIN unpause at L1, then `[SUBSTACK placeholder, L0]`, then password-auth's `pam_env`, `pam_faildelay`, `pam_unix sufficient` and `pam_deny required` at L1 (taken from the host's `/etc/pam.d/password-auth`), then postlogin, which has no auth lines on the host.

| Typed | Inline or `include` (today) | `substack` |
|---|---|---|
| Correct PIN | PIN returns `PAM_SUCCESS` → `done` → positive, decision made at level 0 → **unlock** | `done` ends only the screenlock-pin substack. password-auth then runs: `pam_unix` sees `PAM_AUTHTOK` = the PIN (`pam_get_authtok` returns the stored item without prompting, `libpam/pam_get_authtok.c:119-124`), fails, and as `sufficient` is ignored. `pam_deny` `required` → `bad` → negative. **Unlock refused**, even though the PIN checker already accepted the PIN. Fails closed, but the PIN can never work. |
| Correct password | PIN ignored, `pam_unix use_first_pass` succeeds (`ok`), PIN unpause runs, then the stock password-auth succeeds again → unlock | Same → unlock |
| Wrong password (and no PIN match) | `pam_unix` fails → `die` → decision made at level 0 → refused at once. The stock password-auth never runs. | `die` ends only the substack, already negative. password-auth then runs anyway, with a second unix_chkpwd check on the same wrong secret (an extra "password check failed" log and audit record), a `pam_faildelay` request, and `pam_deny`. Still **refused**: `ok` cannot overturn a negative stack (`pam_dispatch.c:211-219`). |
| pam_screenlock_pin.so missing | PIN line `PAM_MODULE_UNKNOWN` → `default=ignore`. PIN unpause `optional` → ignore. Password works. | Same |

**Verified** by tracing the code paths cited above. The PIN-unlock row of the substack case is **Inferred** in one respect: that the host's `password-auth` keeps its current shape, which authselect may regenerate.

So `substack` is unusable for screenlock-pin unless the stock `auth substack password-auth` were also changed, which defeats the purpose.

### What if the included file is missing? Lockout.

- If `/etc/pam.d/screenlock-pin` is missing, is unreadable by the uid the greeter runs as, or the include target is mistyped, the include line becomes a must-fail handler. Every action is `bad`, the return code is `PAM_PERM_DENIED`, and it sits at level 0 ahead of everything else. The rest of the stack still runs, but the stack is already negative, and `ok`/`done` from `password-auth` cannot overturn it. **Every unlock attempt fails, including the correct password**. **Verified** in `pam_handlers.c:219-222` and `pam_dispatch.c:96-98, 211-219, 240-247`. Recovery would then need a TTY login or `loginctl unlock-session`. The same holds for `substack` (the placeholder is skipped, then the must-fail handler fails), and the `-` prefix doesn't help.
- Contrast this with today's inline block: if the module file disappears, the PIN lines are ignored and the password still unlocks. The inline block's only hard dependency is that `pam_unix.so` exists, and so does the stock stack's.
- The kscreenlocker greeter's PAM worker runs as the locked user, not as root. **Inferred** from kscreenlocker's design and from pam_unix needing the unix_chkpwd helper. So an included file must be world-readable, 0644 like `/etc/pam.d/kde`, and labelled `etc_t` or `pam_conf_t`-equivalent. An installer that wrote it 0640 root:screenlock-pin, to match screenlock-pin's other files, would lock everyone out.
- Ordering would matter for an include design. Install would write `/etc/pam.d/screenlock-pin` first and add the include line last. Uninstall would remove the include line first and the file last. That much is easy. The real risk is something outside the installer: an admin's `rm`, a configuration manager that purges unknown `/etc/pam.d` files, an ostree `/etc` reset to the image defaults, which would drop both files together and so be safe, or a backup restore of only one of the two files.

### Other subtleties of a separate file

- `/etc/pam.d/screenlock-pin` doubles as a PAM service called `screenlock-pin`. Any program that calls `pam_start("screenlock-pin", …)` gets the PIN-or-password auth stack. Its account, password and session functions fall back to `other` (`pam_dispatch.c:383-405`), which is deny on Fedora and common-* on Debian. This adds no new capability, since the same program could use service `kde`, and the failure budget is enforced in the PIN checker anyway. Still, a name that is unlikely to be used as a real service, following Fedora's `password-auth` pattern (for example `screenlock-pin-auth`), and a header comment saying "include-only, not a service", would be tidy. **Inferred**.
- The included file is read only for `auth` lines, so it cannot accidentally inject account or session lines into `kde`. **Verified** (`pam_handlers.c:141-146`).
- Testing: `crates/pam/tests/stack.rs` already builds its stack from `kde-auth.pam` (`kde-auth.pam:4-5`). An include design would test the same file, and its harness would also need a test for the missing-target case.

## Recommendation for screenlock-pin across distributions

| Mechanism | Lock-screen-only? | Run-time behaviour | Failure if screenlock-pin's files vanish | Upgrades of the host's kde file | Verdict |
|---|---|---|---|---|---|
| Marked inline block in the service file (today) | Yes | Reference | Graceful: missing module → ignored, password works | One edited conffile (rpm `.rpmnew`, ostree keeps local); three lines plus markers to merge by hand | **Keep** for Fedora / Aurora |
| One-line `auth include screenlock-pin-auth`, between markers, with lines in a screenlock-pin-owned file | Yes | Identical (verified) | **Lockout** if the file is missing or unreadable | Same edited conffile; only one line to merge; screenlock-pin's lines change without touching kde | Acceptable alternative, only with a doctor/check that verifies the target before and after, a world-readable file, and strict install/uninstall ordering. The gain does not justify the new failure mode today. |
| `auth substack screenlock-pin-auth` | Yes | **Different**: PIN unlock always refused | Lockout, as above | As above | Reject |
| Debian pam-auth-update profile (service-gated) | Only by one `pam_succeed_if` gate | Different block semantics | pam-auth-update regenerates common-auth | No conffile edit | Reject: module mapped into sudo, sshd and login; scope rests on one line |
| Fedora authselect custom profile | Same as above (password-auth is shared) | Different | Same | No conffile edit | Reject |
| Manual: documented lines for the admin to add | Yes | Reference | Depends on the admin | Admin's problem | The fallback for distros the installer doesn't know, and the only policy-clean route for a Debian .deb |

Details behind the verdict:

- **Fedora and Aurora now.** Keep the inline marked block. Its failure modes are already the gentlest available. A deleted module degrades to password-only. A damaged block is caught by `check`, and uninstall restores from the saved copy. The `/etc` edit is unavoidable with any mechanism, because the lock screen's service file is an `/etc` conffile owned by plasma-workspace (**Verified**), and every distro-level manager only writes shared stacks (**Verified** for pam-auth-update and authselect).
- **If an include is ever adopted** (for example, so that screenlock-pin updates never rewrite `/etc/pam.d/kde`): use `include`, never `substack`. Name the file so it doesn't read as a service. Make it 0644 and give it the right SELinux label. Write it before the include line goes in and remove it after the line comes out. Have `install.sh check` and `screenlock-pin doctor` fail loudly when the line is present but the file is not. Ideally keep the include line between screenlock-pin's markers, so that today's removal logic still applies.
- **Debian and Ubuntu later.** Do not ship a pam-config profile. A .deb must not edit `/etc/pam.d/<kde-service>` from its maintainer scripts (Debian Policy on conffiles, **Inferred**), so the edit stays an explicit admin action: `screenlock-pin`'s installer or command doing the same marked-block edit, after a diff and a yes. The anchor must be distro-specific: on Debian it is likely `@include common-auth` in the kscreenlocker service file, or that file may not exist and the lock screen may fall back to `other` (**unverified**, check on a real system). Do not use `/usr/lib/pam.d`, which Debian treats as unsupported (**Verified**), or `@include` in screenlock-pin's own lines unless the target is Debian-only (**Verified**: a Debian patch only).
- **The second line is distro-coupled.** `[success=ok default=die] pam_unix.so use_first_pass` assumes local `/etc/shadow` users. On hosts with SSSD, LDAP, AD or Kerberos users it would `die` on the correct network password. Before screenlock-pin supports such hosts, either detect them and refuse to install, or replace line 2 with a call into the distro's own password stack. That call can't be a substack with a control clause (**Verified**: substack takes none), so it needs another design. **Inferred**.

## Bonus: PIN-like and rate-limiting pieces in linux-pam

- **pam_tally and pam_tally2** were deprecated in 1.4.0 (`linux-pam/NEWS:228`) and removed in 1.5.0 (`NEWS:175`, "use pam_faillock instead"). Debian's pam-auth-update refuses profiles that mention them (pam-auth-update:66, 733-735, from Debian 1.4.0-5; `debian/changelog` around lines 455-462). Nothing to reuse. **Verified**.
- **pam_faillock** is the nearest analogue to screenlock-pin's failure budget. **Verified** in `modules/pam_faillock`:
  - The policy is `deny` = 3 failures within `fail_interval` = 900 s, after which the account is locked for `unlock_time` = 600 s, or until `faillock --reset` when it is 0. Root is exempt unless `even_deny_root` is set (`faillock.conf:29-55`; defaults in `pam_faillock.c:79-81`). It locks the **whole account**: the password stops working too. screenlock-pin pauses only the low-entropy PIN and keeps the high-entropy password available, which avoids faillock's lock-screen denial-of-service.
  - The store is `/var/run/faillock/<user>`, i.e. `/run`, a tmpfs that a reboot wipes. The file is created mode 0660 and `fchown`ed to **the user** (`faillock.c:55-105`; NEWS:166 notes the 0600→0660 change). Anything running as the user can therefore truncate its own tally. screenlock-pin's budget lives in `/var/lib/screenlock-pin` (mode 1770, group `screenlock-pin`, written only through the setgid PIN checker, `install.sh` `own_dir "$budget_dir" 1770 …`), which the user's processes cannot touch and which survives a reboot.
  - It fails open when it can't open its store. `check_tally` returns `PAM_SUCCESS` on `EACCES` or `ENOENT` (`pam_faillock.c:206-208`), and `write_tally` returns `PAM_SUCCESS` on `EACCES` (`pam_faillock.c:321-323`). On the host, `/run/faillock` is `drwxr-xr-x root root`. So a faillock line run by the unprivileged greeter could never create a tally: it would silently do nothing at the lock screen. **Inferred** from the code and the host's directory mode. This is a concrete argument for screenlock-pin's setgid-helper design over reusing faillock.
  - Its `preauth`, `authfail` and `authsucc` actions and its `account` reset (`pam_faillock.c:500-535` and `561-590`) are the same three-phase shape as screenlock-pin's check, password and `after-password-auth` lines. That shape is a useful precedent when explaining screenlock-pin's stack to reviewers.
- **pam_faildelay, pam_fail_delay and pam_unix's 2 s delay.** libpam keeps the largest delay requested, randomises it, and sleeps only on failure, at the end of `pam_authenticate` (`libpam/pam_delay.c:97-146`; `pam_auth.c:29,38`). pam_unix requests 2 s unless `nodelay` is set (`modules/pam_unix/support.c:719-721`). But if the application sets `PAM_FAIL_DELAY`, libpam calls the application's function instead of sleeping (pam_delay.c:112-131), and kscreenlocker does set it (`main.cpp:275-276`). So delays are advisory and under the application's control. An attacker driving PAM from their own process sets no delay and can run handles in parallel. `unix_chkpwd` itself has no rate limit; its only `sleep(10)` is for being run from a terminal (`modules/pam_unix/unix_chkpwd.c:88-99`). screenlock-pin's `min_milliseconds_before_pin_unlock` is a different mechanism, a minimum delay on *success* enforced inside the module, and its budget is enforced by the PIN checker, so neither depends on the application. **Verified** for the code; the comparison is **Inferred**.
- **pam_timestamp** caches a *successful* authentication per user and tty for 5 minutes by default, with an HMAC key in `/var/run/pam_timestamp/_pam_timestamp_key` (`modules/pam_timestamp/pam_timestamp.c:81-84`). It needs root to write (the check at line 804). It has nothing to do with PIN rate limiting, but it is relevant to screenlock-pin's planned sudo scope: it is the in-tree precedent for root-owned, HMAC-protected, time-limited auth state under `/run`. **Verified**.
- Nothing in linux-pam implements a secondary low-entropy secret with a lockout that falls back to the primary secret. screenlock-pin's model has no in-tree counterpart. **Verified** from the module list in `linux-pam/modules/`, where no such module exists.
