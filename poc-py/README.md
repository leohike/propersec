# lazypass

A short_password for the KDE Plasma lock screen. Two words run through everything here:

- **full_password:** your account password. It is long, and it works everywhere, always.
- **short_password:** a short extra password, digits or letters. It unlocks the lock screen and nothing else, and only while it is allowed.

You type either one into the same field. Everywhere else (SDDM login, sudo, polkit, TTY, SSH) the full_password is the only way in. The point is to let the full_password be long without typing it thirty times a day.

**Status: proof of concept.** The tests run entirely inside temporary directories and touch nothing on the system. Installing it into the real lock screen is a separate step, described in INTEGRATION.md.

## How it behaves

The short_password is either **allowed**, or the **full_password is required**.

- **The full_password allows it.** Every full_password unlock at the lock screen allows the short_password, with the failed unlock count back at 0 and a fresh window. After boot the full_password is required until the first such unlock; there is no login hook, so the SDDM login doesn't count.
- **It is allowed for 8 hours** after the last full_password unlock, counted in time since boot, suspend included. After that the full_password is required.
- **Three failed unlocks.** After three failed unlocks in a row the full_password is required. A failed unlock is any input of short_password length that isn't the short_password, so a short mistyped full_password counts too. A correct short_password resets the count but doesn't extend the 8 hours; only the full_password does.
- **Longer than a short_password is free.** The short_password is at most 12 characters (`max_short_password_len`). Anything longer, which is almost always the full_password, is refused at once: it isn't hashed and doesn't count as a failed unlock.
- **Harmless mistakes are free too.** Empty input, input that isn't UTF-8, or input containing a NUL byte can never match, so it fails without counting as a failed unlock.
- **Fails closed.** A missing or damaged file, wrong ownership or permissions, a broken config, a state file from an earlier boot, or any error at all means the full_password is required. The full_password itself always works.

## The pieces

| File | What it is |
|---|---|
| `src/pam_hook.py` | The unlock path's process: pam_exec runs it as the locked user. It reads the command line, PAM's environment and stdin, and turns the result into an exit code. It has two commands: `check` tests the typed input, and `start-short-password-window` runs after a correct full_password. A third, `self-test`, is for `just lazypass smoke` only and never appears in a PAM line. |
| `src/core.py` | The unlock path's decisions, with no process around them: `UnlockAttemptHook`, called with the typed input, and `start_short_password_window_upon_successful_unlock`. |
| `src/cli.py` | The management CLI, installed as the `lazypass` command: `set`, `remove`, `status`. `set` and `remove` need root once installed. |
| `src/common.py` | What the hook and the CLI share. `Settings` holds the short_password hash and the rules for it: it checks a new short_password, verifies typed input, and makes the decision (`get_reason_to_refuse_without_checking`). `ShortPasswordState` is what the state file holds. `UserFiles` is one user's files and the rules for trusting them. `Yescrypt` hashes and verifies through the system's libxcrypt. Plain functions cover the file format. |
| `pam/kde-auth.pam` | The three PAM lines lazypass adds to `/etc/pam.d/kde`. The tests build their stack from this file. |
| `pam/kde` | The whole `/etc/pam.d/kde` that `deploy-pam` installs: the image's vendor file with the three lines inserted above `auth substack password-auth`. Generated by `render-pam`; a test keeps it equal to the vendor file in `backup/kde` plus `pam/kde-auth.pam`. |
| `src/tests/` | Unit, hook and full-PAM-stack tests. See the Testing section. |
| `deploy.py` | Installs `src/` into `/usr/local/libexec/lazypass`, links `/usr/local/bin/lazypass`, creates `/etc/lazypass/users`, fixes SELinux labels (`install`, with sudo); checks every path's owner, mode, content and label (`check`); runs the deployed copy as you (`smoke`). Separately, `install-pam`, `backup-pam`, `restore-pam` and `render-pam` handle `/etc/pam.d/kde`; `install` never touches it. |
| `lazypass.just` | `test` and `test-all`; `deploy`, `check-deploy` and `smoke`; `deploy-pam` (activates lazypass), `restore-pam` (puts a backup back), `backup-pam` and `render-pam`. All but the tests run `deploy.py`. |
| `backup/kde` | The copy of `/etc/pam.d/kde` made by `backup-pam`, from before anything was installed. `backup-pam` never overwrites it with a different file. |
| `WALKTHROUGH.md` | One unlock traced through PAM and the code, line by line. Start here to understand it. |
| `INTEGRATION.md` | What these tests cannot prove, and the steps for installing it, still to be done together. |
| `docs/short-password-security-analysis.md` | The long version of the threat model: what the short_password costs in security, when the hash cost matters, the repeated-access gap, and ideas considered for later versions. |
| `docs/reusing-linux-pam-code.md` | What Linux-PAM's own code teaches a later C or Rust version: how pam_unix verifies, and how pam_timestamp and pam_faillock solve lazypass's window and failure count. Inspiration, not a fork. |

System `python3` and the stdlib only, no virtualenv: the hook runs inside the lock screen's PAM stack. The scripts start with `python3 -ISB`, which ignores `PYTHON*` variables and user site-packages, keeps the script's own directory off the import path, and writes no bytecode.

## Files, once installed

| Path | Holds | Owner and mode |
|---|---|---|
| `/etc/lazypass/config` | Global policy, optional | `root:root 0644` |
| `/etc/lazypass/users/<user>` | That user's yescrypt hash, plus optional per-user policy | `root:<user's private group> 0640` |
| `/run/user/<uid>/lazypass.state` | The `ShortPasswordState`: boot id, `short_password_enabled_at`, `failed_unlock_count` | the user's own, on tmpfs, so it is gone at reboot |
| `/run/user/<uid>/lazypass.lock` | Keeps two attempts from interleaving | the user's own |

All of them are plain `key = value` lines, for example:

```
# /etc/lazypass/users/<user>
hash = $y$j9T$...
max_failed_unlocks = 2
```

## Settings

They go in the global config, or in a user's file to override it for that user. A value outside its range is an error, which means the full_password is required; it is never quietly clamped.

| Setting | Default | Range | Meaning |
|---|---|---|---|
| `expiry_hours` | 8 | 0.01 to 168 | How long the short_password is allowed after a full_password unlock |
| `max_failed_unlocks` | 3 | 1 to 10 | Failed unlocks in a row before the full_password is required |
| `max_short_password_len` | 12 | 1 to 64 | Longest short_password, in characters. `set` refuses longer ones, and the lock screen refuses longer input without hashing or counting it. Lowering it below an existing short_password's length makes that short_password unusable until it is set again. |
| `min_length` | 4 | 1 to 64 | Shortest short_password `set` accepts |
| `min_letters` | 0 (off) | 0 to 64 | English letters `set` requires, upper or lower case |
| `hash_cost` | 5 | 1 to 11 | yescrypt cost `set` hashes with: 5 takes about 20 ms here, 8 about 160 ms |

Why root, if the hook runs as the user: anything the user can write, someone sitting at the unlocked desk for ten seconds can write too. If the hash were user-writable they could plant a short_password they know. If the policy were user-writable they could raise the failed unlock limit and guess at leisure. So both belong to root, and `set` asks for the full_password through sudo.

## Threat model

**Protects against:** someone at the keyboard of a locked machine. They get three guesses each time the short_password is allowed, then need the full_password, and the short_password works nowhere but the lock screen. It also protects against someone at an unlocked desk who wants to plant a short_password for later, because that takes root.

**Does not protect against:**

- **Code already running as you.** It can unlock the session directly (`loginctl unlock-session`), so the short_password changes nothing for it. It can also read the hash and crack a 4-character short_password offline in seconds, so never reuse the short_password anywhere else, such as a bank card or phone PIN.
- **Someone watching you type.** The failed unlock limit stops guessing, not watching. A long full_password resists shoulder-surfing better.
- **Attacks on a running or suspended machine.** While it is on, the disk encryption key is in RAM, and cold-boot or DMA attacks ignore the lock screen entirely, however strong the full_password. Only shutting down (or hibernating to encrypted swap) closes that gap.

**Repeated access** (a coworker, a housemate) is a known gap, left for later: a correct short_password resets the failed unlock count, so someone who can come back again and again gets 2 quiet guesses every time you step away. docs/short-password-security-analysis.md works it through.

**Known limits, by design:** the failed unlock count and `short_password_enabled_at` live in a file the user owns, and the hash is readable by the user. Only code running as the user can exploit either, and that code doesn't need to.

## Testing

```
just lazypass::test        # everything that leaves no trace outside a temporary directory
just lazypass::test-all    # also the two tests that make pam_exec log to the system journal
```

There are three layers, about 83 tests, taking about 15 seconds:

- **Unit tests** (`test_common.py`): the file format, policy limits, the libxcrypt binding (including the NUL-byte truncation trap), the file-safety checks, the state file, and every reason the full_password can be required.
- **Hook tests** (`test_hook.py`, `test_cli.py`): the real scripts run as subprocesses, with the environment and stdin pam_exec would give them, plus the CLI's set, remove and status.
- **Deploy tests** (`test_deploy.py`): `deploy.py` installs into a temporary root owned by the test's user, then `check` and `smoke` run against it, including what `check` reports for a wrong mode, a stale copy, a stray file and a misdirected link. Also the hook's `self-test`, and the PAM file: `install-pam` backs up, activates, and is undone by `restore-pam`; it refuses on anything but `y`, when the code isn't deployed, or when the vendor file has changed since `pam/kde` was made; `pam/kde` equals the vendor file plus the tested lines.
- **PAM tests** (`test_pam.py`): the real libpam and the real `pam_exec.so` run the shipped control lines through `pam_start_confdir`, which loads PAM files from a temporary directory instead of `/etc/pam.d`. Only `pam_unix` is faked, by `src/tests/fake-pam-unix`. Each test also checks that every input produces exactly one prompt.

The PAM tests do catch real mistakes. As a check, changing the shipped `default=die` to `default=ignore`, so a wrong full_password would allow the short_password again, makes two of them fail.

Two cases need the real system and are not covered: how the real `pam_unix` behaves, and how the real greeter behaves. INTEGRATION.md lists them. The CLI's interactive terminal prompt (getpass) is untested as well; the tests feed the short_password on stdin.
